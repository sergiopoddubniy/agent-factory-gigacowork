# Концепция: агент как продукт, спецификация как источник правды

Версия 1 · 2026-09-21

## Что такое Фабрика агентов GigaCowork

Общее решение, с помощью которого сотрудник клиента — аналитик,
методолог, владелец процесса — делает рабочего агента на GigaCowork сам:
от идеи до пакета, приёмки и подтверждённого результата. Консультант не
нужен, программист не нужен. Если входной информации не хватает, фабрика
не останавливается и не додумывает: она выводит из дыр спецификации план,
что и у кого узнать, и собирает демо на явных допущениях.

Частный случай — пилот у клиента: аналитики 1С собирают в фабрике ассистента
1С-разработки и сравнивают его с таким же агентом, собранным их командой
на собственном стеке (план пилота — в папке клиента, в репозиторий не входит).

## Откуда взято

Три источника, и у каждого — своя роль.

**Скилл `gigacowork-agent-scenario` (v9.10)** — движок: формат пакета
GigaCowork (семнадцать разделов, фронтматтер — зеркало формы «Создать
навык», одна команда), проверки на Python с честными кодами возврата,
полевое исследование с эталонными разборами как оракулом, уровни доступа
L0–L3, маркеры `missing_data` / `conflict_requires_review` /
`HITL_REQUIRED`, переиспользование до проектирования. Фабрика — его
издание для конечного пользователя, а не для консультанта.

**AI-DISRUPT PDLC (white paper v3.7)** — рамка. Документ сам разводит две
вещи: SDD как контракт изменения классической ИТ-системы (§2.5) и
Agent Specification как первичный артефакт агентного продукта в отдельном
контуре (§2.15): предмет — поведение, приёмка — поведенческие проверки,
DoD — гипотеза результата измерена. Фабрика реализует контур §2.15. Из
него взяты: Discovery как обязательные артефакты, а не этап; гипотеза
результата в четырёх–шести полях; осознанное решение «адаптация или
перепроектирование»; класс применимости, задающий глубину Discovery;
HITL-карта таблицей; пакет доказательств как контракт завершения;
принцип «Discovery before generation»; антипаттерны «Discovery как театр»,
«спецификация как длинный тикет», «спецификация как ТЗ».

**Spec-Driven Development (Spec Kit, Kiro, Tessl)** — дисциплина:
спецификация — источник правды; производное порождается из неё; правка
идёт в спецификацию, не в результат; недоопределённые места находятся
машиной и превращаются в вопросы; синтаксис EARS («Когда <условие>, агент
должен <ответ>») для требований, которые читает и человек, и проверка.

## Что фабрика делает иначе, чем исходный скилл

| | Скилл (консультант) | Фабрика (пользователь) |
|---|---|---|
| Кто заполняет | консультант по интервью | пользователь по вопросам оркестратора |
| Артефакт-источник | карточка сценария (yaml) + пакет пишется руками | `AGENT_SPEC.md` из 15 блоков; пакет порождается скриптом |
| Достаточность | правило «продолжай с допущениями» | два порога, считает `spec_readiness.py`; ниже demo пакет не порождается |
| Недостаток информации | план исследования пишется консультантом | план выводится из дыр `consulting_plan.py` |
| Результат | KPI 2–4 в карточке | гипотеза результата в шести полях, статус проверки в контракте завершения |
| Improvement loop | правка пакета и проверка | правка спецификации → пересборка → отпечаток сверяется |
| Объём контекста | SKILL.md ~25k токенов, references ~131k | SKILL.md ~5k (маршрут), стадии режимов и справочники читаются по ссылке |
| Комплект поставки | собирается по стадиям руками, сверяется `check_delivery.py` | порождается из спецификации `build_delivery.py` по тому же целевому составу, сверяется тем же `check_delivery.py` |

Что не изменилось намеренно: формат пакета, целевой состав поставки,
правила аудита и сверки, маркеры, уровни доступа, требование эталонных
разборов, «один агент — одна джоба», три режима и четыре задачи. С V3
фабрика содержит исходный скилл целиком — консультант и пользователь
работают одним инструментом, разница только в том, кто заполняет
спецификацию.

## Пять решений

1. **Спецификация — markdown, а не yaml.** Читается бизнес-пользователем,
   правится в любом редакторе, разбирается стандартной библиотекой без
   зависимостей, диффится в git. Машиночитаемость обеспечивают
   канонические заголовки блоков и строки «Поле: значение».
2. **Два порога, не один.** Demo — можно показать; pilot — можно
   измерять. Между ними — план добора. Без второго порога получается
   «Discovery без валидации»: агент показан, эффект не измерен.
3. **Молчание запрещено, допущение разрешено.** `Допущение:` и
   `Не знаем:` — законные состояния блока; пустой блок — нет.
4. **Ворота считают содержание, а не наличие текста.** Поля гипотезы,
   строки EARS, строки HITL-таблицы, id случаев. Это защита от «Discovery
   как театр».
5. **Определение «сделано» — гипотеза проверена.** Пакет доказательств
   порога pilot не READY, пока статус гипотезы — «не проверена».

## Чего в фабрике нет и почему

Governance Mesh, IDP, лестница R0–R5 как runtime, Guardian Agents,
метрики платформы — уровень корпорации, у фабрики нет такого рантайма;
white paper сам выносит это за периметр PDLC. Генерация кода — не задача
агента фабрики. Клиентских данных в репозитории нет: реестр реализованных
агентов наполняется на машине консультанта, база шаблонов — только
синтетикой и обезличенными наборами.
