# 06 · Политика обезличивания

Версия 2 · 2026-09-28. Действует для двух поставок из одного репозитория:
открытого GitHub и витринной сборки плагина для платформы GigaCowork
(`scripts/build_hub.py`). Правило одно: клиентское не публикуется; провенанс
уроков — то, откуда правило взялось, — остаётся там, где он нужен
консультанту, и вырезается там, где он не нужен никому.

## Три класса содержимого

| Класс | Что | GitHub | Витрина |
|---|---|---|---|
| **A · запрещено везде** | названия компаний-клиентов и их групп, имена людей, бренды контрагентов из клиентских кейсов, домены компаний, ИНН и реквизиты, реальные документы клиентов, внутренние названия подразделений и продуктов заказчика, абсолютные суммы сделок и отчётности, точные параметры методик клиента | нет | нет |
| **B · провенанс** | даты пилотов и встреч, хронология («восьмой случай», «после встречи»), псевдонимы клиентов в связке с датой, шаблон адреса инстанса платформы, формулировки «на боевом прогоне <платформа> выяснилось» | да | нет — вырезается сборкой |
| **C · разрешено везде** | правила и их иглы в проверках, синтетические примеры и материалы, псевдонимы клиентов без хронологии, публичные реестры и сервисы (ЕИС, Федресурс), публичные бенчмарки, относительные величины («расхождение 7 %», «на порядок больше итога») | да | да |

Псевдонимы — `Клиент-<буква>` для компаний, `ДатаРеестр` для провайдера
данных, `ООО «Пример-Контрагент»` для контрагента в примерах, `example.ru` и
`example-<роль>.ru` для доменов. **Соответствие псевдонимов реальным именам в
репозиторий не входит** — оно хранится у автора вне Git; по той же причине в
репозитории нет и стоп-листа реальных названий.

## Как пишется новый урок

Правило — отдельным абзацем, повод — отдельной фразой, начинающейся со слова
`Повод:` (`Повод: боевой прогон у Клиент-К, 13.09.2026`). Сборка витрины
убирает даты и фразы-поводы механически, правило остаётся целиком; иглы
`selftest_delivery.py` ставятся на правило, а не на повод. Суммы — только
относительные; домены — только `example-*.ru`; людей не бывает даже по
инициалам.

## Как проверяется

`scripts/hub_gate.py` — единственный источник правил проверки:

- **строгий режим** (витрина): даты `дд.мм.гггг`, суммы с ₽/руб/млн/млрд в
  абсолютных величинах, домены вне белого списка, ФИО с отчеством,
  орг-форма с названием в кавычках, стоп-слова платформы, псевдонимы в
  связке с датой — ноль вхождений, иначе сборка красная;
- **мягкий режим** (репозиторий, CI): только класс A по общим признакам
  (домены вне белого списка, ФИО, орг-форма с названием в кавычках);
- необязательный приватный стоп-лист (`--стоп-слова <файл>`, файл вне Git)
  — для локальной проверки по реальным названиям. Стоп-слово ловится с
  начала слова (короткое название внутри длинного обычного слова — не
  находка); строка
  `re:<регулярка>` — для имён, которые совпадают с началом обычного слова.

Чего шлюз не видит — и что поэтому ищется глазами при каждом новом
референсе. Перенос семнадцати шаблонов (V3.4) показал три класса, которые
прошли регулярки: одиночные фамилии без имени и отчества («разбор
конструктора — <фамилия> / <фамилия>»), номера документов клиента в именах
файлов (номера ТП, ТЗ, извещений) и абсолютные цифры клиента внутри
«контрольных цифр прогона». Приватный стоп-лист тогда же нашёл остатки
в уже опубликованных справочниках и коде — имена проектов в примерах
`id`, названия клиента и провайдера данных в комментариях и регулярках
детекторов. Правило: после переноса — поиск по фамильным окончаниям и
частым именам, по номерам документов и по суммам с проверкой, чьи они;
детекторы в коде называют признак, а не поставщика.

Шлюз ловит признаки, а не смысл: если урок можно опознать по деталям без
единого запрещённого слова, его переписывают. Проверка чужими глазами перед
публикацией новой версии обязательна (`agent_templates.md`, тот же принцип).

## Витрина и GitHub — чем отличаются

Витринная сборка (`scripts/build_hub.py`, результат в `dist/`) — это
`plugin/agent-factory` **без референсов** — по требованию платформы: без
`examples/`, без шаблонов в `references/agent_templates/` (база пуста,
индекс пересобран на ноль), с пустыми копилками (`knowledge/registry.yaml`,
`log.md`), без провенанса класса B — обёрнутый в раскладку плагина
платформы (`templates/hub/`). Агент на платформе проектируется с нуля по
спецификации и собирается скриптами — референс ему для этого не нужен. Всё
остальное совпадает с репозиторием байт в байт, включая скрипты и проверки:
`selftest_delivery.py` и строгий шлюз внутри витрины обязаны быть зелёными,
`selftest.py` — на источнике сборки (ему нужен пример). Это доказательство,
что вырезан провенанс, а не правила.

## Референсы: где живут и как наполняются

Референс — обезличенный пример полного пути «спецификация → комплект»
(`examples/`) и шаблон агента в базе шаблонов (`references/agent_templates/`).
Пример 1С-разработки синтетический от первой до последней строки. База
шаблонов с V3.4 — восемнадцать агентов по пяти функциям: пример 1С и
семнадцать обезличенных навыков из пилотов и воркшопов (логистика, сбыт и
маркетинг, закупки и тендеры, консолидация отчётности); у каждого — роль,
джоба, происхождение и карта переноса. Референсы
**живут и накапливаются в открытом репозитории** — это решение автора: они
питают блок 14 «Переиспользование», подбор шаблона по джобе и прогоны на
Sonnet; в витринную сборку они не переносятся.

Наполнение — после каждого пилота: `promote_finding.py` переносит находку в
справочник, `templates.py` добавляет обезличенный шаблон с происхождением
`синтетика` или `обезличено` (не `реальное`), карта переноса называет, что
заменить; новый референс проходит `hub_gate.py --мягко` с приватным
стоп-листом, а находки строгого режима разбираются глазами: даты пилотов,
номера документов и фамилии вырезаются, пороги и иллюстративные суммы
примеров остаются. Затем — проверка чужими глазами до попадания в версию. Так репозиторий богатеет уроками и
примерами, не приобретая ни одного клиентского факта, а витрина остаётся
тем, чем её хочет видеть платформа.
