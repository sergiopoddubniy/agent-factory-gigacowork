# Пилот Пулково: ассистент 1С-разработки через фабрику

Версия 1 · 2026-09-21 · связан с пакетом ФЭО в папке клиента
(`ФЭО/ФЭО_ассистент_1С_оценка_и_границы_пилота`, `Подход_к_оценке_1С_на_странице`,
`Оценка_1С_один_слайд`).

## Что доказываем

Одна методология, три бейзлайна: Б0 — против нуля (ворота, меряет сам
проект Пулково); Б1 — против агента на стеке, доступного только
программисту (тезис «понятнее и проще»); Б2 — против сборки того же агента
на текущем стеке (предложение Щеглова: часы по ролям, дни до приёмки).
Обе сборки делают люди Пулково; Сбер не собирает, не измеряет и не
принимает. Фабрика — инструмент второй сборки.

## Как фабрика ложится на десять дней

| День | Что происходит | Что делает фабрика |
|---|---|---|
| 0 | ворота подписаны, приёмочные критерии владельца процесса, плагин на тестовом инстансе, журнал часов включён | `spec_readiness.py --threshold pilot` на спецификации, заполненной по критериям владельца — красные находки = вопросы дня 0 |
| 1–5 | 2–3 аналитика 1С учатся фабрике и собирают агента на GigaCowork без Сбера; журнал часов по ролям и обращений за помощью | `/новый-агент` → `AGENT_SPEC.md`; `/ворота`; `/комплект` (пакет, карточка, команды, docx, база знаний, синтетика — по целевому составу); загрузка по инструкции по сборке; часы аналитиков — это и есть измерение Б2 |
| 6 | приёмка обеих сборок по одним критериям владельца процесса, вслепую | `/приёмка`: прогон по блоку 12, `EVIDENCE_BUNDLE.md` порога demo |
| 7–8 | 6–10 типовых задач (ТЗ по требованию; вопросы к конфигурации) на обоих агентах, слепая приёмка | те же задачи — предметные случаи блока 12; факт и вердикт в файл прогона |
| 9–10 | метрики доступности, ретроспектива сопровождения, расчёт, карточки на подпись, коэффициенты для переноса | `/результат`: статус гипотезы, `EVIDENCE_BUNDLE.md` порога pilot; коэффициенты — в ФЭО |

## Что Discovery уже сделан

Discovery агента 1С у клиента сделан их собственным проектом. Фабрика его
не повторяет, а принимает на вход: приёмочные критерии владельца процесса
→ блок 12; задачи дней 7–8 → предметные случаи; драйверы Б1/Б2 из ФЭО →
блок 3; слепая приёмка дня 6 → прогон. Спецификацию своего агента клиент
не раскрывает — и не должен: `AGENT_SPEC.md` в фабрике заполняют его же
аналитики, это их артефакт. Именно он делает агента «понятным
бизнес-пользователю» — тезис Б1 проверяется на том, что аналитик без
программиста доходит от идеи до пакета.

## Честность сравнения Б2

У команды стека Discovery уже оплачен проектом. Значит, в часы фабрики он
либо не входит (спецификация заполняется по готовым критериям — дни 1–2),
либо входит у обеих сторон. Решение фиксируется в день 0 и записывается в
`СБОРКА.md`. Иначе Б2 сравнивает сборку с «сборкой плюс исследование».

Что ещё фиксируется в день 0: статус INFATON MCP и среда разработки;
генерация кода исключена (1С:Напарник бесплатен до 01.10.2026);
поколение конструктора на инстансе.

## Гипотеза результата для этого агента

Пример заполнения — `plugin/agent-factory/examples/1c-dev-assistant/AGENT_SPEC.md`,
блок 3: метрика — часы аналитика на ТЗ по запросу; бейзлайн — по журналу
или хронометражу (не со слов); цель — с защитной метрикой «доля принятого
без правок»; период — 28 дней на 10 запросах; условие пересмотра — доля
принятых ниже 50 % к 14-му дню. Б1 и Б2 — отдельные гипотезы в ФЭО, у них
свои метрики (время до первого рабочего агента у непрограммиста; часы по
ролям до приёмки); в спецификацию агента они не пишутся, чтобы не было
двойного счёта.

## Что нужно от платформы до дня 0

Плагин установлен на тестовом инстансе; Python-скрипты запускаются;
рабочая область позволяет писать комплект; поколение конструктора
известно. Список вопросов — `03_Валидация_для_платформы.md`.

## Что не входит и сказано заранее

Генерация кода, боевые интеграции (L2+), статистическая значимость,
стабильность после релиза. Минимальный формат в одну неделю — только Б2.
