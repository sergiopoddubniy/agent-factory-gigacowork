## Состав репозитория

```text

├── ЖУРНАЛ_ВЕРСИЙ.md

├── runs/                         — прогоны на Sonnet: промпты, ответы, вердикты, отчёты
└── plugin/agent-factory/         — то, что уходит на платформу

    │                               /результат /портфель /пилот
    ├── references/               — 38 справочников: 7 фабрики + 30 исходного скилла (дословно)
    │   ├── pipelines/            — single_agent, portfolio, pilot_upgrade — стадии и этапы целиком
    │   ├── agent_templates/      — база шаблонов (спецификация + порождённые файлы, синтетика)
    │   └── knowledge/            — реестр реализованных агентов (в репозитории пуст)
    ├── templates/                — AGENT_SPEC.template.md, ПРИЁМОЧНЫЙ_ПРОГОН.template.md
    ├── scripts/                  — 31 скрипт, только stdlib (7 фабрики + 20 исходного скилла + 4 новых)

                │            └──► <корень>_загрузка/<slug>.zip (архив вне поставки, SHA-256)
                ├──► build_agent_package.py  (render_skill/render_command — 17 разделов, Режим 0, шлюз на источник)
                ├──► check_package.py        (structural audit пакета + отпечаток спецификации)
                ├──► check_delivery.py       (сверка с целевым составом: Я1–Я21, надстройки, связность СВ/О, Н, Я19–Я21)
                └──► evidence_bundle.py      (контракт завершения: READY / NOT READY по порогу)

ПРИЁМОЧНЫЙ_ПРОГОН.md ──► evidence_bundle.py;  evals_<slug>.md + прогон_<дата>.md ──► check_run.py
```

Единственный разбор спецификации — `factory_common.py`; все скрипты
читают её через него, поэтому ворота, план, сборка и доказательства не
могут разойтись в трактовке. Уровни проверок — четыре, у каждого свой
инструмент, и ни один не заменяет соседний: сам скилл (`selftest.py`,
`selftest_delivery.py`, `mutate_*`), комплект (`check_delivery.py`), пакет
(`check_package.py`), развёрнутый агент (`check_run.py`).

## Спецификация как контракт

Фронтматтер (id, имя, версия, дата, класс, контур, доступ) и 15 блоков с
каноническими заголовками. Статус блока вычисляется: заполнено /
допущение (`Допущение:`) / отсутствует; строка `Не знаем:` — явный пробел.
Отпечаток — SHA-256 по NFC-тексту, 8 hex-знаков — ставится в пакет
(`спецификация: <id> · <версия> · <отпечаток>`) и сверяется аудитом.

Пороги (`spec_readiness.py`):

| | demo | pilot |
|---|---|---|
| блоки 1, 5, 6, 7, 12 | заполнены | заполнены |
| остальные | допущение разрешено, молчание нет | ни одного отсутствующего |
| блок 3 | поля, если заполнен | шесть полей; бейзлайн не допущение; метрика не намерение |
| блок 9 | ≥ 1 строка EARS | ≥ 3 |
| блок 10 | таблица, если заполнен | строки с ролью в «Кто» |
| блок 8 (ии-нативный, агентный) | — | `Чек-лист полноты:` ≥ 5 пунктов, у каждого критерий закрытия |
| блок 12 | 5 обязательных id | + ≥ 2 предметных |
| блок 13 | явно (может быть «Не знаем») | ≥ 2 эталона |
| блок 15 | — | владелец процесса назван |
| класс детерминированный | блоки 2, 4 не требуются | то же |

## Порождение пакета

Таблица «блок → раздел» — в `references/package_format.md`. Части навыка,
не зависящие от задачи (§9, §12, §14, §17, каркас §7), — фиксированный
текст сборщика: так каждый агент фабрики соблюдает конвенции платформы
одинаково. Части, зависящие от задачи (§1–§6, §8, §10, §11, §13, §15,
§16), — из блоков. Шаги блока 8 со стрелкой `→` становятся модулями §6 с
входом и выходом.

**Единица результата.** `Чек-лист полноты:` блока 8 — не совет агенту, а
структура, из которой сборщик порождает форму результата: таблица ровно из
N строк с тремя статусами (`закрыто` / `вопрос` / `конфликт`), якорем и
номером вопроса, строка сверки K+Q+C=N, таблица критериев закрытия
(«`закрыто`, если …» — по одному на пункт, описана один раз), модуль 0
«опись» как первый проход, одностороннее правило о расхождениях, гейт
`completeness_check`. Реестр вопросов к заказчику = строки `вопрос` и
`конфликт`. Это перенос уровней 1–5, 7 и 9 справочника `output_stability`
исходного скилла в порождаемый текст; результат на прогонах: S1 — реестр 1
vs 3 вопроса между сессиями, S4 — 10/10 статусов в трёх сессиях
(`references/output_stability.md`).

## Порождение комплекта

`build_delivery.py` порождает из спецификации всё, что порождается (карточка
с блоком активации и `**id:**`, команды `N.0`/`N.1`/… с телами, журнал
изменений с версией и датой, карта состава базы знаний с происхождением и
режимом, README синтетики с порядком показа по случаям блока 12, точка входа,
инструкция по сборке с шагами Я12 и проверкой задеплоенного состояния,
карта джоб, след переиспользования из блока 14, клиентский docx по шести
разделам `scenario_template.md`, приёмочные кейсы `evals_<slug>.md` с
машинными признаками, файл прогона из ответов агента, надстройки задачи:
Д1–Д3 / В1–В2 / П1–П13). Руками кладутся только знание клиента (`--kb`) и
данные (`--synthetic`, `--calibration`). Сборщик отказывает, если файл базы
знаний, объявленный в блоке 6, не передан (`Ф-БЗ`): комплект без базы
знаний — заготовка. Сверка с целевым составом — оригинальный
`check_delivery.py` исходного скилла: на примере — PASS 55/55 ядра и
11/11, 10/10, 21/21 надстроек для трёх задач.

## Что остаётся человеку

Интервью и решения по каждой находке — оркестратор предлагает
формулировку, пользователь подтверждает. Прогон — ручной, вердикт по
ожиданию из спецификации. Измерение гипотезы — по методике блока 3.
Скрипты не заменяют суждение; они не дают его пропустить.
