## Результат

Номер ТЗ: ______   Дата: 2026-09-21   Инициатор: руководитель отдела закупок (ФИО в письме не указано)   Аналитик: ______   Статус: черновик

### 1. Цель и обоснование
Дать инициатору заявки на закупку возможность указывать основание закупки (номер проекта, договор, служебная записка) прямо в заявке, чтобы согласующий видел его без дополнительной переписки, а при оформлении заказа поставщику основание автоматически переносилось в заказ. Проблема бизнеса: согласующие сейчас запрашивают основание закупки отдельной перепиской. Заказчик — руководитель отдела закупок (источник: письмо «Доработка заявки на закупку — основание»).

### 2. Объекты конфигурации
- **Документ.ЗаявкаНаЗакупку** — добавить новый реквизит. Предложение аналитика по техническому имени (требует подтверждения, не вопрос заказчику): `ОснованиеЗакупки`, тип Строка(200), синоним «Основание закупки», на уровне метаданных необязательный — обязательность проверяется программно только при переводе в статус «На согласовании» (см. §3 п.2). Источник: письмо, абз. 1.
- **Документ.ЗаказПоставщику** — реквизит `ОснованиеЗакупки` (Строка(150)) уже существует (выгрузка, реквизит 006); менять его тип по письму не просили, но реквизит — целевой для переноса из заявки, а его длина меньше длины нового поля заявки. Расхождение — Вопрос №4.
- **Форма списка** Документ.ЗаявкаНаЗакупку (ФормаСписка) — добавить колонку «Основание закупки» (письмо, п.3).
- **Форма документа** Документ.ЗаявкаНаЗакупку (ФормаДокумента) — вывести поле для заполнения инициатором и просмотра согласующим (письмо, п.1, п.3).
- **Обработка.СоздатьЗаказПоЗаявке** — доработать: по выгрузке сейчас «Реквизит ОснованиеЗакупки заказа не заполняет»; нужно, чтобы значение из нового реквизита заявки переносилось в реквизит «ОснованиеЗакупки» заказа при создании заказа по заявке (письмо, п.4).
- **Документ.ПоступлениеТоваровУслуг** — доработки не требует: реквизит «ОснованиеЗакупки» уже копируется из заказа автоматически (выгрузка, реквизит 006) — после заполнения поля в заказе оно дойдёт и до поступления без дополнительных изменений.

### 3. Функциональные требования
1. Инициатор заполняет реквизит «Основание закупки» при создании заявки на закупку. Условие срабатывания: создание заявки. Ожидаемое поведение: поле доступно для ввода текста до 200 символов. Источник: письмо, п.1.
2. При попытке перевода заявки в статус «На согласовании» система проверяет заполненность «Основание закупки»; если поле пустое — перевод запрещается, выводится сообщение «Укажите основание закупки». Источник: письмо, п.2. Кто именно выполняет перевод статуса — не определено (Вопрос №1), критерий приёмки будет уточнён после ответа.
3. Согласующий видит значение «Основание закупки» в форме заявки и в списке заявок отдельной колонкой. Условие: открытие формы/списка заявок. Источник: письмо, п.3.
4. При создании заказа поставщику по согласованной заявке (обработка «Создать заказ по заявке») значение «Основание закупки» переносится из заявки в одноимённый реквизит заказа. Источник: письмо, п.4; выгрузка, Обработка.СоздатьЗаказПоЗаявке (текущее поведение — поле не заполняет). Ограничение длины целевого поля — Вопрос №4, конкретный способ переноса (обрезка/увеличение поля) агент не выбирает.

### 4. Печатные формы
Не применяется: заказчик прямо указал не менять печатные формы («Печатные формы менять не нужно», письмо). Существующая печатная форма «Заказ» уже использует реквизит «ОснованиеЗакупки» заказа (выгрузка, макет ПФ_Заказ) — после доработки в неё будет попадать перенесённое из заявки значение без изменения самого макета.

### 5. Права доступа
Определяется ответом заказчика (Вопрос №2). Письмо ролей доступа к новому реквизиту не называет, права доступа не входят в состав выгрузки конфигурации (примечание выгрузки: «права доступа ... не включены»).

### 6. Миграция данных
Определяется ответом заказчика (Вопрос №3). Заказчик не сообщил, нужно ли и как заполнять «Основание закупки» для уже существующих заявок и заказов.

### 7. Критерии приёмки
1. Инициатор создаёт заявку на закупку и заполняет «Основание закупки» → значение сохраняется вместе с заявкой.
2. Попытка перевести заявку с пустым «Основание закупки» в статус «На согласовании» → перевод блокируется, выводится сообщение «Укажите основание закупки».
3. То же действие с заполненным полем → статус меняется на «На согласовании» без ограничений.
4. Согласующий открывает форму заявки и список заявок → значение «Основание закупки» видно в форме и отдельной колонкой списка.
5. По согласованной заявке формируется заказ поставщику через обработку «Создать заказ по заявке» → значение «Основание закупки» перенесено в заказ (способ переноса — по решению вопроса №4).
6. Критерии по правам доступа и по миграции существующих документов будут добавлены после ответов на вопросы №2 и №3.

### Реестр открытых вопросов к заказчику
1. Кто выполняет перевод заявки на закупку в статус «На согласовании» — инициатор или другой пользователь? В письме не указано; из выгрузки видно только, что при этом переводе назначается «Согласующий» (реквизит 007), а не кто выполняет сам перевод.
2. Какие роли/пользователи должны иметь доступ на просмотр и на редактирование нового реквизита «Основание закупки» в заявке и в заказе? В письме роли не названы, права доступа не входят в выгрузку.
3. Нужно ли заполнять «Основание закупки» для уже существующих (ранее созданных) заявок на закупку и заказов поставщику, и если да — как именно?
4. В письме реквизит «Основание закупки» заявки описан как текстовое поле до 200 символов, а в выгрузке одноимённый реквизит документа «Заказ поставщику» (куда, по п.4 письма, значение должно переноситься) — Строка(150), то есть короче на 50 символов. Гипотеза аналитика (не решение): либо увеличить длину поля заказа до 200 символов, либо ограничить поле заявки 150 символами, либо переносить значение с усечением до 150 символов — решение за заказчиком/архитектором 1С.

## Неопределённости и допущения
- `missing_data`: роли доступа к новому реквизиту «Основание закупки» — не заданы письмом, не входят в выгрузку (Вопрос №2).
- `missing_data`: правило миграции существующих заявок/заказов без заполненного основания — не задано заказчиком (Вопрос №3).
- `conflict_requires_review`: длина нового реквизита заявки (200 символов) больше длины существующего одноимённого реквизита заказа (150 символов), в который требуется перенос значения (Вопрос №4).
- Не установлен явно исполнитель перевода заявки в статус «На согласовании» (Вопрос №1) — из выгрузки известно только, кто назначается согласующим в этот момент, а не кто выполняет сам перевод.
- Допущение аналитика, не вопрос заказчику и не конфликт: предлагаемое техническое имя нового реквизита — `ОснованиеЗакупки` (по аналогии с одноимённым реквизитом заказа), тип Строка(200) — требует подтверждения при постановке задачи разработчику.
