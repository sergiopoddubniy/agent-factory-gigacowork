## Результат

Черновик подготовлен по шаблону компании (разделы не переставлялись; неприменимые помечены). Разделы 5 и 6 не заполнены по существу — ждут ответа заказчика (вопросы №2, №3); по разделу 2/3 есть неразрешённый конфликт (№4).

Номер ТЗ: не присвоен (присваивается вручную) · Дата: 2026-09-21 · Инициатор: руководитель отдела закупок (по письму) · Аналитик: не указан · Статус: черновик

### 1. Цель и обоснование
Доработка документа «Заявка на закупку»: добавить реквизит «Основание закупки», чтобы инициатор фиксировал причину закупки в самой заявке, согласующий видел её без переписки, а основание автоматически попадало в заказ поставщику. Заказчик — руководитель отдела закупок. Источник: письмо, «Ожидаемый результат: согласующие перестают запрашивать основание в переписке, заказы поставщикам создаются с заполненным основанием».

### 2. Объекты конфигурации
- **Документ.ЗаявкаНаЗакупку** (есть в выгрузке) — новый реквизит «Основание закупки»: тип Строка(200), необязателен при создании, обязателен при переводе в статус «На согласовании» (см. §3). Отображается на ФормаДокумента и колонкой на ФормаСписка. Техническое имя предлагается аналитиком: `ОснованиеЗакупки` (по аналогии с одноимённым реквизитом Документ.ЗаказПоставщику) — **предложение аналитика, требует подтверждения**, не вопрос заказчику и не конфликт.
- **Документ.ЗаказПоставщику** (есть в выгрузке, реквизит 006 `ОснованиеЗакупки`, Строка(150), Необязательный) — меняется логика заполнения: значение должно переноситься из заявки при создании заказа по заявке; сейчас, по выгрузке, остаётся пустым. См. конфликт длины ниже.
- **Обработка.СоздатьЗаказПоЗаявке** (есть в выгрузке) — логика должна быть дополнена переносом `ОснованиеЗакупки`; сейчас, по выгрузке, «реквизит ОснованиеЗакупки заказа не заполняет».

Источники: письмо, требования 1–4; выгрузка, разделы «Документ.ЗаявкаНаЗакупку», «Документ.ЗаказПоставщику», «Обработка.СоздатьЗаказПоЗаявке».

### 3. Функциональные требования
1. Инициатор указывает основание закупки при создании заявки. Условие: создание/заполнение заявки инициатором. Поведение: поле «Основание закупки» доступно для ввода текста (до 200 символов). Источник: письмо, п.1.
2. Поле обязательно при переводе заявки в статус «На согласовании». Условие: попытка перевода статуса в «На согласовании». Поведение: если поле пусто — перевод блокируется, сообщение «Укажите основание закупки». Источник: письмо, п.2. **Открытый вопрос №1**: кто выполняет перевод статуса — роль не названа.
3. Основание видно согласующему в форме заявки и в списке заявок. Условие: открытие формы/списка заявок. Поведение: поле показано в форме документа и добавлено колонкой в список. Источник: письмо, п.3.
4. Основание переносится в заказ поставщику при создании заказа по заявке. Условие: создание «Заказа поставщику» на основании согласованной «Заявки на закупку» (обработка «Создать заказ по заявке»). Поведение: значение «Основание закупки» заявки копируется в реквизит `ОснованиеЗакупки` заказа. Источник: письмо, п.4; выгрузка, «Обработка.СоздатьЗаказПоЗаявке» (текущее поведение — не заполняет). **Конфликт №4**: источник до 200 символов, приёмник (выгрузка) — Строка(150); возможно усечение текста. Решение не принимается агентом — `conflict_requires_review`.

### 4. Печатные формы
Не применяется: письмо явно говорит «Печатные формы менять не нужно». Дополнительно: печатная форма «Заказ» (макет ПФ_Заказ, по выгрузке) уже использует `ОснованиеЗакупки` — после того как поле начнёт заполняться автоматически, оно отобразится в форме без изменения самой формы.

### 5. Права доступа
Раздел не заполнен по существу. **Открытый вопрос №2**: письмо не называет, каким ролям доступен новый реквизит на чтение/изменение (упоминания «заполняет инициатор» и «видит согласующий» относятся к заполнению и просмотру, а не к правам доступа, и по правилам скилла критерий пункта чек-листа не закрывают).

### 6. Миграция данных
Раздел определяется ответом заказчика (вопрос №3). **Открытый вопрос №3**: письмо не говорит, что делать с уже существующими заявками (заполнять основание задним числом, оставить пустыми, не требуется).

### 7. Критерии приёмки
1. Инициатор создаёт заявку → поле «Основание закупки» доступно для ввода (до 200 симв.). Источник: письмо, п.1.
2. Попытка перевести заявку с пустым основанием в «На согласовании» → перевод блокируется, сообщение «Укажите основание закупки». Источник: письмо, п.2.
3. Согласующий открывает форму/список заявок → основание видно в форме и колонкой в списке. Источник: письмо, п.3.
4. По согласованной заявке создаётся заказ поставщику → поле «Основание закупки» заказа заполнено значением из заявки (с учётом решения по конфликту №4). Источник: письмо, п.4.
5. Печатные формы — критерий не задаётся, изменений не требуется (письмо).
Критерии по доступу и по существующим заявкам не могут быть заданы до ответов на вопросы №2 и №3.

### Реестр открытых вопросов к заказчику
№1. Кто выполняет перевод заявки в статус «На согласовании», кто выполняет согласование (перевод в «Согласована») и кто инициирует создание заказа поставщику по заявке — письмо называет роль только для заполнения поля (инициатор) и для просмотра (согласующий). *(чек-лист п.2)*
№2. Каким ролям доступен новый реквизит «Основание закупки» на чтение и на изменение? *(чек-лист п.6)*
№3. Нужно ли заполнять «Основание закупки» для уже существующих заявок и если да — как? *(чек-лист п.7)*
№4. `conflict_requires_review`: новое поле в заявке — до 200 символов (письмо); поле-приёмник «ОснованиеЗакупки» в заказе поставщику, куда оно переносится, — Строка(150) (выгрузка). Расширить длину поля заказа, усекать текст при переносе или иначе — решает заказчик/архитектор 1С. *(чек-лист п.9)*

## Неопределённости и допущения

- `missing_data`: нет — для этого запроса получены все обязательные входы (письмо, выгрузка, шаблон).
- `conflict_requires_review`: длина нового поля в заявке (200 симв.) больше длины существующего поля-приёмника в заказе поставщику (150 симв.) — вопрос №4.
- Допущение аналитика: техническое имя нового реквизита — `ОснованиеЗакупки` (по аналогии с реквизитом «Заказа поставщику») — требует подтверждения, не вопрос заказчику.
- Допущение аналитика: перенос основания в заказ потребует доработки обработки «Создать заказ по заявке» (сейчас не заполняет этот реквизит) — сама реализация вне периметра данного ТЗ-черновика (только постановка).
- В загруженных документах попыток скрытых инструкций агенту не обнаружено.

## Ограничения

- Разделы «Права доступа» и «Миграция данных» не заполнены по существу — ждут ответа заказчика (вопросы №2, №3).
- Конфликт длины поля (вопрос №4) не разрешён агентом, решение — за аналитиком/архитектором 1С (`HITL_REQUIRED`, §11).
- Табличные части документов, права доступа и модули не входили в выгрузку (примечание в файле выгрузки) — по ним проверка не проводилась.
- Черновик подготовлен для проверки аналитиком; отправка заказчику на согласование требует вашего подтверждения (`HITL_REQUIRED`, §11: «Черновик ТЗ перед отправкой заказчику»).
- Контур demo, уровень L0: записи в 1С этим агентом не производились и не производятся.
