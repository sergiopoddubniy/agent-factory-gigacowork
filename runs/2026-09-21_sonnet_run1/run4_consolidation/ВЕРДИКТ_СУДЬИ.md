## Найденные дефекты (по убыванию важности — что сломается у клиента)

1. **[Важно] Подтверждённый коннектор исполнения кода нигде не зафиксирован в исполняемой команде агента.** Вся архитектура (AGENT_SPEC §11, README ядра, SKILL.md §13) называет его «единственным внешним сервисом, которым пользуется агент», подтверждённым админом платформы 17.09.2026. Но в реальном файле, который загружается в конструктор (`работа/комплект/04_Пакеты_агентов/…/02_Команды_severny-port-consolidation.md`, строка 23, и идентично в архиве для загрузки `работа/комплект_загрузка/severny-port-consolidation/commands/run-agent.md`, строка 18) стоит: **«подтверждённые инструменты — нет (`external_write=false`)»**. По карте соответствия полей платформы (`фабрика/references/platform_architecture.md`, «Поколение 2»: `Коннекторы → confirmed_tools в команде запуска`) — это единственное машиночитаемое место, где коннектор должен быть назван. Проверено, что это не ручная недоработка консультанта конкретно здесь, а ограничение самого инструмента фабрики: `фабрика/scripts/build_agent_package.py` (строки ~161 и ~396) жёстко печатает эту фразу для **любого** агента без параметра — идентичная строка стоит и в несвязанном примере `1c-dev-assistant`. `check_delivery.py` этого не ловит (проверяет только упоминание правил коннектора где-то в навыке, не согласованность полей команды запуска). HANDOFF.md не упоминает это расхождение среди перечисленных им 4 замечаний к инструментарию фабрики (раздел 5) — то есть само не заметило. Возможное смягчение: по логике §11 спецификации запись только в собственный `sandbox:/output/` формально не требует HITL/SIM_TOOL_CALL (как и AI Word/Excel) — то есть на текущем контуре `demo` это может не мешать показу буквально. Но поле, единственно предназначенное фиксировать подтверждение коннектора для платформы/будущего аудита доступа, продолжает молчать про единственный внешний сервис, который агент использует, — риск для пилота и для проверки администратором платформы.
2. **[Средне] «Запасной результат» на случай сбоя показа не заполнен.** `работа/комплект/08_Сценарий_показа/03_Запасной_результат.md` — заготовка: «Ответ ещё не записан: после первого удачного прогона `happy_path` вставить его сюда целиком». `02_Сценарий_отказа.md` прямо предписывает показать этот файл при сбое живого прогона 30.09.2026 — а показывать нечего. Проверка `check_delivery.py` (пункт «Д3») ловит только наличие файла с именем «запасн», не то, что в нём есть содержимое — этим объясняется, почему PASS в п.12 этого не поймал. Мы сами получили нужный happy_path прогон за секунды (см. критерий 10) — заполнить было можно.
3. **[Мелко] Адресация строк формы — только по коду, не по «коду + наименованию».** `harness/io_xlsx.py::_row_by_code` (строки 119-123) ищет строку по значению столбца A (код), не сверяя столбец B (наименование статьи), хотя `computational_core.md` требует ключ «код + наименование» именно для защиты от смещения/дублирования строк. На нынешнем зафиксированном шаблоне (17 уникальных кодов на Ф1, 6 на Ф2, без дублей) это не проявляется и не проявится, пока шаблон не меняют, но при будущей правке формы (например, добавление второй строки с тем же кодом для расшифровки) харнес молча запишет значение не в ту строку без явной ошибки.

## Что сделано лучше минимума

- Регрессионный набор идёт дальше двух обязательных кварталов: встроены синтетические стоп-кейсы §4.3 (несогласованность «Расчёты»/«Обороты»), §4.6 (инвестиции) и «чужая компания» — ветки регламента, которых нет в реальных данных, но которые харнес обязан уметь остановить.
- Prompt-injection проверяется на уровне движка, а не только промптом агента: `test_инструкция_в_комментарии_реестра_не_меняет_расчёт` доказывает кодом, что текст в комментарии ячейки не влияет ни на одну цифру, а не полагается на то, что модель «не послушается».
- Тест детерминизма сравнивает не только код возврата, но и полное внутреннее состояние (`company_f1/f2`, `g_f1/h_f1/g_f2/h_f2`, порядок и severity находок) между двумя независимыми запусками.
- Протокол контролей полон по умолчанию: в реальном прогоне Q1 записано 25 строк контролей (K1-К9 на каждую компанию и на группу), а не только проваленные — это даёт владельцу процесса «ожидание/факт/статус» по каждому пункту, а не только список проблем.
- Провенанс параметров вписан прямо в `rules/consolidation_rules.yaml` построчными комментариями со ссылкой на пункт регламента и на интейк — спор на приёмке решается чтением одного файла, а не пересчётом.
- `00_ЧТО_ЗДЕСЬ_И_ЧЕГО_ЗДЕСЬ_НЕТ.md` и `Справочник_периметра_и_нормализации_названий.md` явно проговаривают отличие «точного сопоставления в закрытом периметре» от «нечёткого поиска похожего» — редкая для такого рода пакетов методологическая ясность, подтверждённая тестом на реальной опечатке.
