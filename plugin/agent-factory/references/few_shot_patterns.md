# few_shot_patterns.md — архетипы few-shot примеров

Во всех трёх собранных до сих пор сценариях (АМПЕРУС, ПК Балтика, ЧерриДом)
одна и та же комбинация из четырёх архетипов оказалась достаточной, чтобы
демо за 12–15 минут убедительно показывало и «агент справляется», и «агент
не халтурит там, где данные неоднозначны». Используй именно эти четыре —
не подменяй их четырьмя случайными кейсами.

## Архетип 1 — Эталонный / штатный случай

Агент получает чистый, полный вход и всё проходит гладко: все шаги
алгоритма выполнены, оценка высокая, явных проблем нет.

Зачем нужен: показывает базовый happy path и служит визуальным эталоном
формата вывода (на него удобно ссылаться в Примере 4 — «вот как выглядит
хорошо»).

Примеры из практики:
- ПК Балтика: штатный визит в Пятёрочку, отставание по обороту небольшое.
- ЧерриДом: эталонный звонок (5/5 этапов, возражение отработано на 5).
- АМПЕРУС: штатный запрос на подбор оборудования, все параметры заданы.

## Архетип 2 — Проблемный случай / эскалация

Агент получает вход с явным нарушением, пропуском шага или выходом за
стандартные рамки — и должен это заметить, а не сгладить. Часто дополняется
вторым файлом-контекстом (карточка сделки/ТТ/клиента), который показывает,
что проблема была предсказуема заранее — это самый сильный «вау-момент»
демо, потому что видно, что агент реально читает контекст, а не просто
классифицирует.

Примеры из практики:
- ПК Балтика: фото полки с нарушением фейсинга + карточка ТТ.
- ЧерриДом: проблемный звонок + карточка сделки, где риск был помечен заранее.
- АМПЕРУС: запрос с параметром вне стандартной линейки → эскалация инженеру.

Опционально в эту же категорию — «противоречие в данных» (АМПЕРУС: письмо
говорит одно число, таблица — другое): агент должен явно попросить уточнения,
а не выбрать значение сам. Если у клиента процесс подразумевает несколько
источников на один кейс (письмо+таблица, звонок+CRM-карточка,
фото+спецификация) — обязательно закладывай такое противоречие.

## Архетип 3 — Консультативный режим (без загрузки файла)

Сотрудник задаёт вопрос агенту напрямую, без входного документа — агент
отвечает на основе RAG-базы, не дожидаясь конкретного кейса. Показывает, что
агент полезен не только как анализатор документов, но и как база знаний
«на лету».

Примеры из практики:
- ПК Балтика: «как убедить категорийного менеджера ввести бренд, он говорит
  нет спроса» → мини-питч из brand_portfolio.md.
- ЧерриДом: «как лучше отвечать на возражение про долгострой» → техника из
  objections_playbook.md.

## Архетип 4 — Агрегация / системный паттерн

Агент получает несколько объектов одного типа (несколько звонков одного
менеджера, сводная таблица по точкам продаж, серия запросов) и должен не
просто разобрать каждый по отдельности, а найти закономерность, которая не
видна при разборе одного кейса. Это второй сильный «вау-момент» — агент
формулирует вывод уровня «это не случайность, это система», с конкретной
рекомендацией по приоритету.

Примеры из практики:
- ПК Балтика: падение оборота -35% в одной точке — разбор причин по
  ассортименту, фейсингу, истории.
- ЧерриДом: 3–4 звонка одного менеджера подряд — во всех пропущен один и тот
  же шаг алгоритма (next step), это и есть системный вывод.

## Как это переносится в синтетические данные

Каждый архетип должен буквально соответствовать одному или нескольким
файлам в `02_demo_input_files/`, и файл(ы) должны быть явно связаны с
номером примера в README демо-пакета (таблица «шаг → файл → команда →
результат»). Если для архетипа 2 используется связка «основной файл +
файл-контекст» — оба файла должны описывать один и тот же объект/сделку/ID,
а не два разных — иначе демо выглядит склеенным из случайных кусков.

Числа и пороги внутри демо-файлов должны совпадать с тем, что задано в
`01_rag_knowledge_base/` (пороги 🟢🟡🔴, границы линейки продукта, шкала
оценки и т.п.) — рассинхрон здесь моментально заметен на встрече, если
клиент захочет пересчитать вручную.

## Связь few-shot примеров с acceptance cases пакета

Few-shot примеры в клиентском docx и acceptance cases в `SKILL.md` — это два
представления одного и того же набора проверок. Собирай их одновременно,
иначе демо и пакет разъедутся.

| Архетип few-shot | Acceptance case в пакете |
|---|---|
| 1 — эталонный / штатный случай | `happy_path` |
| 2 — проблемный случай / эскалация | `conflicting_sources` (если используется противоречие в данных) |
| 3 — консультативный режим без файла | дополнительный case, не входит в обязательный минимум |
| 4 — агрегация / системный паттерн | дополнительный case, не входит в обязательный минимум |

Три обязательных case не имеют пары среди архетипов и на встрече обычно не
показываются, но в пакете присутствуют всегда:

- `missing_required_input` — отсутствует обязательный вход → `missing_data`;
- `prompt_injection_in_document` — во входном документе инструкция изменить
  правила агента → игнорируется;
- `external_action_without_confirmation` — требуется внешнее действие →
  `HITL_REQUIRED`, write-back не выполняется.

Последние два стоит **упомянуть словами** на встрече, даже не показывая: для
ИБ-специалиста клиента это часто более весомый аргумент, чем сам разбор
документа. Особенно если в проекте уже поднимался вопрос разграничения
доступа и фильтрации чувствительных данных.
