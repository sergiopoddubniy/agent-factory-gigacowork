# Пайплайн: портфель (мастерская воркшопа)

## Режим: портфель (мастерская воркшопа)


Режим «портфель» фабрики: N агентов к одному событию. Текст — из
оркестратора исходного скилла; в фабрике **у каждого агента портфеля своя
спецификация `AGENT_SPEC.md`** (папка агента в `02_Discovery_спецификация/<N>_<slug>/`),
а спецификация портфеля — отдельный файл `00_Спецификация_портфеля.md` с
объявленным уровнем агентизации. Этапы 4–5 и 7–8 — это стадии одиночного
агента (Стадия 1–4 одиночного режима, `single_agent.md`) на каждого агента, с
`build_delivery.py --номер <N> --out <общий корень>`: сборщик кладёт агента
в ту же поставку рядом с остальными (папка = агент, префикс команд `N.`).

### Когда

Клиент просит агентов для нескольких ролей/процессов сразу, обычно к
единому демонстрационному событию — воркшоп, презентация возможностей
отдела/компании. Вход — как в одиночном режиме («Когда это применимо»
выше), но на несколько процессов одновременно: обычно сырые
транскрипты/чаты нескольких установочных встреч, а не один интервью, и
явное решение о треке и периметре с самого начала (какие бизнес-функции в
скоупе — не постфактум).

### Артефакты на выходе

| Артефакт | Файл(ы) |
|---|---|
| Реестр идей / спецификация портфеля / аудит идей / гэп-чеклист — **рабочие артефакты, в пакет поставки не входят** | `00_Спецификация_и_дизайн/*.md` |
| Пакет агента ×N | `06_.../04_Пакеты_агентов/<N>_<slug>/` — **папка на агента**: `00_Навык_<slug>.md`, `01_Карточка_агента_<slug>.md`, `02_Команды_<slug>.md`, `03_Спецификация_<slug>.docx`. **Архивов в поставке нет**: конструктор Поколения 2 принимает архив, и упаковывает его человек по инструкции Я6 |
| Клиентский docx ×N | `02_Сценарии_агентов_docx/*.docx` — сценарий для клиента; спецификация агента живёт в папке агента |
| Синтетика ×N | `03_Синтетика_для_демо/<N>_<slug>/` — файлами, без архива |
| Калибровочные данные (реальные документы клиента) — **не выносятся на демонстрацию** | `04_Калибровочные_данные/<N>_<slug>/` |
| Интеграции (если нужен кастомный коннектор) | `05_Интеграции/` |
| Единое пространство | `06_Единый_Workspace_для_воркшопа/` (база знаний + описания + команды + пакеты + мастер-инструкция + мастер-сценарий) |
| **Карта джоб** | `00_Карта_джоб.md` — обязательна для всех задач, не только для демонстрации; для демонстрации к ней добавляется сценарий отказа, Этап 9 |
| **Точка входа для человека** | `00_Как_использовать_этот_комплект.md` |

Перечень выше — **раскладка по путям, а не источник состава**. Что именно
обязано быть в комплекте, задано в `references/delivery_composition.md`;
там же таблица соответствия «элемент → путь» для всех трёх задач. Перед
выдачей — блокирующая сверка `scripts/check_delivery.py`; для портфеля она
выполняется на Этапе 10, вместе с аудитами.

### Пайплайн

Шаги портфеля нумеруются как **Этапы**, чтобы не путать их со **Стадиями**
режима «одиночный агент»: у двух пайплайнов свои нумерации, и «Этап 5» —
это сборка пакетов портфеля, тогда как «Стадия 5» — handoff одиночного
агента. Везде ниже: Этап = портфель, Стадия = одиночный агент.

```text
[Этап −1. ПОЛЕВОЕ ИССЛЕДОВАНИЕ — если на входе только записи встреч;
 `discovery_research.md`. Для портфеля обязателен разбор случая по одной
 роли на волну и эталонные разборы для агентов, работающих с документами]
Этап 0. INTAKE ПОРТФЕЛЯ (первым решением — УРОВЕНЬ АГЕНТИЗАЦИИ:
        `agentization_level.md`; он задаёт единицу состава портфеля)
   → 1. РЕЕСТР ИДЕЙ → 2. СПЕЦИФИКАЦИЯ ПОРТФЕЛЯ
   → 3. FIT CHECK И ВОЛНЫ → 3б. КАРТА РЕШЕНИЯ (дерево артефактов + приоритет)
[ЧЕКПОЙНТ ОДОБРЕНИЯ — архитектура портфеля]
   → 4. АРХИТЕКТУРА ПО АГЕНТАМ (= Стадия 1 одиночного режима, на каждого)
   → 5. СБОРКА ПАКЕТОВ (= Стадия 2 одиночного режима, на каждого)
   → 6. ЕДИНАЯ БАЗА ЗНАНИЙ ПРОСТРАНСТВА
   → 7. ДОКС-СЦЕНАРИИ ПО АГЕНТАМ (опц.; = Стадия 3 одиночного, на каждого)
   → 8. СИНТЕТИКА ПО АГЕНТАМ (= Стадия 4 одиночного режима, на каждого)
   → 9. МАСТЕР-СЦЕНАРИЙ ПОКАЗА (воркшоп или демонстрация — см. задачу;
        для демонстрации сюда же входят КАРТА ДЖОБ и СЦЕНАРИЙ ОТКАЗА,
        `references/demonstration_mode.md`)
   → 10. МАСТЕР-ИНСТРУКЦИЯ СБОРКИ ПРОСТРАНСТВА
[ЧЕКПОЙНТ ОДОБРЕНИЯ — комплект перед аудитом]
   → 11. АУДИТ ИДЕЙ-В-АРХИТЕКТУРЕ → 12. ГЭП-ЧЕКЛИСТ ПОЛНОТЫ
   → 13. ГЛОБАЛЬНЫЙ АУДИТ СОГЛАСОВАННОСТИ
   → 13б. ПРОВЕРКА ГИПОТЕЗАМИ (selftest + мутации и метаморфные отношения
          на одном агенте волны как представителе)
[ЧЕКПОЙНТ ОДОБРЕНИЯ — находки аудита]
   → 14. ПРЕЗЕНТАЦИЯ ВОРКШОПА (опционально) → 15. HANDOFF
```

**Спецификация портфеля объявляет уровень агентизации первой же шапкой** —
внутренний (единица состава — джоба) или рыночный (единица — сторона сделки).
Не «подразумевается по составу», а строкой: единица состава портфеля решает,
что считать одним агентом, и молчаливо выбранная единица разъезжается с
составом на второй волне. Для рыночного уровня в спецификации обязательны
таблица «команда → единица результата» и произнесённое вслух отступление от
правила «агент = одна джоба» — см. `agentization_level.md`, «Правило замены».

Этапы 0–3 — читай `references/portfolio_intake.md` целиком, включая
чекпойнт одобрения после Этапа 2. Этапы 4–5 не имеют собственного текста
здесь: выполни Стадию 1 и Стадию 2 режима «одиночный агент» буквально, один
раз на каждого агента, в порядке волн, не по номеру. На Этапе 5 build-kit
Поколения 1.5 собирается через `references/agent_card_kit.md` и
`scripts/build_agent_card.py` — **не** `build_agent_package.py`, тот жёстко
проверяет «ровно 1 навык, 1 команда», это другая структура, не параметр
запуска. Этап 6 — читай `references/workspace_assembly.md` целиком, это
самая объёмная новая работа режима: имена навыков `<N>_<slug>`, дублирование
`SKILL.md` в базу знаний, префиксы команд в общем плоском пуле. Этапы 7–8 —
Стадии 3 и 4 одиночного режима, на каждого агента волны. Этапы 9–10 —
`references/master_scenario_template.md` и `references/workspace_assembly.md`
соответственно. Этапы 11–13 — `references/portfolio_audit.md` целиком, все
три проверки обязательны, ни одна не заменяет другую. Этап 13б —
`references/hypothesis_testing.md`: три аудита отвечают на «собрано ли по
правилам», проверка гипотезами — на «а что если правила неверны». Перед
воркшопом обязательна: на живой сессии дефект проверки виден при клиенте. Этап 14 —
опционально, разовый документ для kickoff/старта воркшопа, стандартный цикл
проверки docx/pptx-скилла. Этап 15 — как «Стадия 5 — Handoff» одиночного
режима, но `present_files` в порядке: все пакеты → все docx → все
синтетики → единое пространство целиком, плюс мастер-инструкция сборки
(не только инструкция загрузки одного пакета).

### Что не менять при переносе с одиночного режима

Волны — по силе демонстрационного эффекта (например, агент с живой
интеграцией обычно сильнее агента той же сложности на чистой синтетике), не
по порядку в исходном списке клиента. Один сценарий — один агент остаётся
верным и внутри портфеля: у каждого из N разных бизнес-процессов — свой
одиночный агент, портфель не превращает несколько агентов в один
мультиагентный оркестратор и не превращает один сценарий в несколько
агентов ради видимости масштаба.
