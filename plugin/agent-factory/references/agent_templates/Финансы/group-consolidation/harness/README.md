# Live harness консолидации отчётности группы

Прототип к вопросу: не является ли Excel-шаблон ошибкой как интерфейс для
LLM-агента. Здесь расчёт вынесен из таблицы в детерминированный движок,
а таблица осталась только формой представления результата.

## Идея

Три функции, которые в Excel-шаблоне были смешаны, здесь разделены:

| Функция | Где живёт | Свойства |
|---|---|---|
| Правила консолидации | `rules/*.yaml` | человекочитаемо, ФД может проверить и подписать, версионируется в git, диффится |
| Выполнение расчёта | `harness/` | детерминировано, покрыто регрессионным тестом, арифметика не зависит от модели |
| Представление результата | выходной `.xlsx` | **тот же файл формы, что на входе**, с консолидированными цифрами |

Роль LLM сужается до того, что она делает хорошо: сопоставить название
статьи с кодом, разобрать неоднозначное написание контрагента, объяснить
расхождение. Адресация ячеек и арифметика уходят в код.

## Выходные формы: заполнение по шаблону исходного файла

Форма не пересобирается заново. Берётся файл одной из компаний, копируется
байт в байт (сохраняются стили, объединённые ячейки, ширины, шапка, все
листы включая пояснения) и в те же самые ячейки вписываются
консолидированные значения.

Следствие: **перечень строк формы задаёт сам файл, а не наш список кодов.**
Строки, которых не было в модели — 1215, вторая строка 1220, расшифровки
2411/2412, блок 2500–2910 — переносятся автоматически и не теряются.

Три нетривиальных места, каждое закрыто инвариантом:

1. **Выравнивание строк.** По номеру строки выравнивать нельзя: у КБ нет
   строки «Налог при УСН», и вся нумерация ниже смещается. Ключ строки —
   код + наименование + порядковый номер повтора.
2. **Выбор шаблона.** Шаблоном берётся компания, форма которой содержит все
   строки остальных. Если такой нет — `NO_SUPERSET_TEMPLATE`, рендер по
   шаблону запрещён.
3. **Адресация элиминации.** Код 1520 встречается дважды («Кредиторская
   задолженность» и «Обязательство по аренде»); целевая строка указана в
   `rules → elimination_target_row`. Если код повторяется и цель не задана —
   `AMBIGUOUS_ELIMINATION_ROW`.

После записи выполняется перекрёстная сверка `FORM_ENGINE_DIVERGENCE`: две
независимые ветки — построчное суммирование по форме и расчёт по кодам в
движке — обязаны сойтись.

## Контур обратной связи (это и есть «live»)

Движок не просто считает — он возвращает агенту машиночитаемые нарушения
с полем `fix_hint`, по которым можно действовать без догадок:

```json
{
  "id": "NEGATIVE_LIABILITY",
  "severity": "BLOCKING",
  "message": "Статья пассива 1520 стала отрицательной после элиминации",
  "fix_hint": "Элиминация списана не на ту строку. Типовая причина — заём
               отнесён на 1520 вместо 1410/1510. Проверьте account_to_line
               для счетов 66/67.",
  "where": {"line": "1520"},
  "actual": -1250000.00
}
```

Агент читает нарушение → правит `rules/*.yaml` или уточняет данные →
перезапускает. При `BLOCKING` результат физически не формируется.

## Запуск

```bash
python run.py check --data data                 # только проверки
python run.py run   --data data --out out       # свод + выходные формы
python run.py adopt-template --from <файл> --approved-by "<ФИО ФД>"
python run.py brief-data --data data --verified-by "<ФИО ФД>"
python -m pytest tests/ -q                      # регрессия: 22 теста
```

Коды возврата: `0` — OK, `2` — есть блокирующие нарушения.

## Инварианты

| id | Уровень | Что ловит |
|---|---|---|
| `MISSING_INPUT_FILE` | BLOCKING | нет файла компании |
| `MISSING_SHEET` | BLOCKING | нет нужного листа в книге |
| `SECTION_SUM_MISMATCH` | BLOCKING | сумма статей ≠ итог раздела (ловит потерю строк с дублирующимся кодом и сдвиг данных) |
| `PL_SECTION_SUM_MISMATCH` | BLOCKING | то же для ОФР, с допуском на округление итогов до тысяч |
| `UNMATCHED_INTERCOMPANY` | BLOCKING | сальдо без встречной стороны |
| `NO_LINE_MAPPING` | BLOCKING | счёт не описан в правилах |
| `ELIMINATION_ASYMMETRY` | BLOCKING | элиминация по активу ≠ по пассиву |
| `NEGATIVE_LIABILITY` | BLOCKING | статья пассива ушла в минус |
| `CONSOLIDATION_IMBALANCE` | BLOCKING | расхождение создано расчётом, а не унаследовано |
| `COMPANY_BALANCE_MISMATCH` | WARNING | актив ≠ пассив в исходной отчётности компании |
| `INHERITED_IMBALANCE` | WARNING | суммарное унаследованное расхождение |
| `SPLIT_MATCH` | INFO | сальдо закрыто несколькими субсчетами (заём = долг + проценты) |
| `OFF_BALANCE_SKIPPED` | INFO | забалансовый счёт исключён |
| `DUPLICATE_CODE_ROWS` | INFO | коды с несколькими строками формы — просуммированы |
| `NO_SUPERSET_TEMPLATE` | BLOCKING | ни одна форма не содержит всех строк остальных |
| `AMBIGUOUS_ELIMINATION_ROW` | BLOCKING | код повторяется, целевая строка элиминации не задана |
| `FORM_ENGINE_DIVERGENCE` | BLOCKING (баланс) / WARNING (ОФР) | заполненная форма разошлась с расчётом движка |
| `COMPARATIVE_PERIODS_CLEARED` | WARNING | колонки прошлых периодов очищены — нет данных для их элиминации |
| `ROWS_ABSENT_IN_COMPANY` | INFO | у компании нет строк шаблона — считаются нулевыми |
| `TEMPLATE_RENDER_OK` | INFO | форма заполнена, указан файл-источник шаблона |

## Сканер входящей отчётности

Перед рендером форма входящих файлов сверяется с эталонным отпечатком
(`rules/template_fingerprint.json`) по контрольным точкам: состав листов,
набор и порядок строк, наличие кодов 1600/1700/2110/2400. Оформление в
отпечаток не входит.

Сравнение несимметрично: эталон — канонический надмножественный состав.
Отсутствие строк у компании нормально (разные налоговые режимы) и даёт
`COMPANY_FORM_SUBSET`; расхождением считается появление строк, которых в
эталоне нет.

| Исход | Поведение |
|---|---|
| `TEMPLATE_MATCH` | рендер по контекстному шаблону, `template_mode: context` |
| `TEMPLATE_DRIFT_NEEDS_CONFIRMATION` | **выходные формы не создаются**; в `where.details` перечислено, что именно разошлось |
| `TEMPLATE_DRIFT_CONFIRMED` | рендер по входящей форме после `--confirm-template-drift` |
| `TEMPLATE_DRIFT_CRITICAL` | блокировка без предложения подтвердить: потеряны итоговые строки |

Два пути разрешения, выбирает пользователь:

```bash
# разовый рендер по входящей форме, эталон не меняется
python run.py run --data data --out out --confirm-template-drift

# новая форма стала штатной — заменить эталон (требует подтверждения ФД)
python run.py adopt-template --from data/Баланс_<код>_<год>.xlsx \
    --approved-by "<ФИО финансового директора>"
```

Без `--approved-by` команда возвращает `REFUSED`: замена эталона меняет
правило приёмки для всех последующих периодов, и это решение человека.

## Аналитическая справка (HITL)

```bash
python run.py brief-data --data data --verified-by "<ФИО>"
```

Без `--verified-by` — `REFUSED`. При незакрытых BLOCKING — `BLOCKED`.
Техническая гарантия того, что справка для руководства не уйдёт по
неподтверждённому своду. Вывод содержит консолидированные показатели,
разрез по компаниям, элиминации, открытые вопросы и `scope_note` о
границах консолидации.

## Выходные файлы

| Файл | Назначение |
|---|---|
| `01_konsolidirovannaya_otchetnost.xlsx` | форма один в один как входная, с консолидированными цифрами — для бухгалтерии, банка, аудитора |
| `02_rabochaya_sverka.xlsx` | рабочая форма с колонками «сумма компаний / элиминация / консолидировано» и таблицей элиминаций |
| `03_report.json` | полный отчёт со всеми findings |

Входные отчёты в выходную папку **не копируются**: они уже есть у
пользователя, а дублирование создаёт риск принять исходник за
консолидированную форму.

## Что показал сам процесс разработки

Пять итераций контура на реальных данных, каждая — реальный дефект:

1. **19 BLOCKING** → итоги ОФР в исходниках округлены до тысяч, а детальные
   строки в рублях. Лечится параметром `materiality.pl_section_rub`, а не
   правкой кода.
2. **2 BLOCKING** → наивный поиск подстроки сопоставлял «Компания Б»
   с «Компания А», компания сверялась сама с собой. Лечится сопоставлением
   от самого длинного совпадающего написания.
3. **0 BLOCKING** → займы разложены на основной долг и проценты; нужно
   сопоставление 1:N, где каждый субсчёт даёт свою строку элиминации со
   своей строкой баланса.

4. **Числовая ячейка со значением 2400 читалась как код строки 2400.**
   Лечится определением колонки кодов один раз на лист, а не «первое
   похожее значение в строке».
5. **Формы компаний оказались не идентичны** — у КБ нет строки «Налог при
   УСН». Выравнивание по номеру строки дало бы сдвиг значений; перешли на
   ключ «код + наименование».

Ни одна из пяти не была бы видна в Excel-шаблоне: там они дали бы просто
неверную цифру без объяснения.

## Ограничения

- Прототип консолидирует баланс и ОФР. Остальные листы формы (ДДС, отчёт
  об изменениях капитала, пояснения) переносятся из файла-шаблона **как
  есть, с цифрами одной компании** — они не консолидированы и должны быть
  либо очищены, либо доработаны до пилота. Это известное ограничение,
  а не готовая функциональность.
- Не проверялось исполнение внутри GigaCowork. По логу прошлого прогона
  агент вызывал `openpyxl` и `xlrd`, то есть исполнение Python на платформе
  есть, но политики в отношении сторонних пакетов (`PyYAML`, `xlrd`) и
  доступа к файловой системе нужно подтвердить до пилота.
- Правила элиминации отражают рабочую гипотезу со слов ФД и не заменяют
  формализованную учётную политику группы.
