# agent_spec.md — спецификация агента: блоки, статусы, класс

Спецификация — один файл `AGENT_SPEC.md`: фронтматтер и пятнадцать
нумерованных блоков `## N. Название`. Заголовки канонические — по ним
работает разбор (`scripts/factory_common.py`), и переименованный блок для
ворот не существует.

## Статусы блока

| Статус | Как распознаётся | Что означает |
|---|---|---|
| заполнено | есть содержательный текст, нет строк `Допущение:` | знаем и записали |
| допущение | есть хотя бы одна строка `Допущение: …` | приняли без подтверждения; уходит в handoff списком и в §16 навыка |
| отсутствует | пусто или только «—» | молчание; на пороге demo запрещено для ключевых блоков, на pilot — для всех |

Отдельная строка `Не знаем: …` — явный пробел. Она не делает блок
заполненным, но и не считается молчанием: из неё план добора берёт
открытый вопрос.

## Фронтматтер

```yaml
id: <клиент>-<джоба>            # латиница строчными через дефис; не меняется никогда
имя агента: <русское имя>       # как увидит пользователь в каталоге навыков
версия спецификации: S1         # растёт при каждой правке: S2, S3 …
обновлено: ГГГГ-ММ-ДД
класс применимости: <детерминированный | ии-помощник | ии-нативный | агентный>
контур: demo                    # demo | pilot | production
уровень доступа: L0             # L0 | L1 | L2 | L3
категория: <в каталоге>         # необязательно
```

## Класс применимости

Четыре признака, ответ занимает минуту:

| Признак | детерминированный | ии-помощник | ии-нативный | агентный |
|---|---|---|---|---|
| неопределённость задачи | нет: шаблон, правило | низкая | средняя | высокая, открытый конец |
| нужная адаптивность | фиксированный сценарий | подсказки, человек принимает | генерация по правилам | автономная декомпозиция |
| цена ошибки | любая (проверяется тестом) | низкая | средняя — нужны приёмочные случаи | высокая — человек в контуре |
| обратимость действий | полная | полная | частичная | любая, с контрольными точками |

Класс задаёт глубину Discovery и плотность проверок: для
детерминированного PR/FAQ и решение об адаптации не требуются; для
агентного в блоке 10 обязательны точки на каждом необратимом действии, а
в блоке 12 — случаи эскалации.

Большинство агентов для рабочих мест — **ии-нативный**: один навык, правила
из блока 8, приёмка по блоку 12.

## Блоки

### 1. Возможность
Зачем нужен агент, что меняется, кто заинтересован. Одна фраза о
результате. Ошибка: описание функций («агент умеет…») вместо изменения в
работе.

### 2. PR/FAQ
Полстраницы «пресс-релиза из будущего» глазами первого пользователя и
3–5 вопросов, которые зададут первые пользователи, с ответами. Сначала
результат, потом технология. Ошибка: пресс-релиз про платформу, а не про
день пользователя. Для детерминированного класса не требуется.

### 3. Гипотеза результата
Шесть строк: `Метрика:`, `Бейзлайн:`, `Цель:`, `Опережающий индикатор:`,
`Период подтверждения:`, `Условие пересмотра:`. Подробно —
`outcome_hypothesis.md`. Ошибки: метрика-намерение («улучшить»), бейзлайн
со слов, период короче, чем природа метрики.

### 4. Адаптация или перепроектирование
`Решение: адаптация | перепроектирование` и `Обоснование:`. Адаптация —
процесс прежний, агент берёт шаги; перепроектирование — шаги
пересматриваются вокруг агента. Решение принимается осознанно и
записывается; по умолчанию побеждает адаптация как путь наименьшего
сопротивления, и тогда новая технология воспроизводит старый процесс.
Обязательный вопрос: «как выглядело бы перепроектирование?».

### 5. Пользователь и триггер
`Роль:` (должность, отдел) и `Триггер:` (что запускает работу). Один
агент — одна роль.

### 6. Входы и выходы
Списки `Входы:` и `Выходы:` с форматами. Входы — документы и данные, а не
«информация»; выходы — артефакты, которые можно показать.

### 7. Периметр
`In-scope:` и `Out-of-scope:`. Out-of-scope — два-три соседних запроса,
которые легко перепутать. Именно из него порождается вторая часть поля
«когда применять» в навыке: «Не бери навык, если …».

### 8. Правила и критерии решений
Три части, в таком порядке. **Правила** — реестр решений: признак → порог →
что делать при неоднозначности. **`Чек-лист полноты:`** — нумерованный
список того, что агент обязан закрыть по каждому запросу (объект, роль
каждого действия, результат, тип и длина, обязательность, права, миграция,
печатные формы, расхождения с данными, параметры отчёта…). Каждый пункт
несёт **критерий закрытия**: `<пункт> — закрыто, если: <что именно должно
быть названо в источнике>`. Без критерия агент сам решает, закрыт ли пункт,
и в двух сессиях решает по-разному (косвенное упоминание «кто видит поле»
один раз сходит за права доступа, другой — нет). Это единица результата:
сборщик порождает из чек-листа таблицу критериев и таблицу результата в §8
навыка с тремя статусами (`закрыто` / `вопрос` / `конфликт`), якорем и
строкой сверки, шаг «опись» в §7 и гейт `completeness_check` в §14 — реестр
вопросов к заказчику становится строками `вопрос`/`конфликт` и перестаёт
плавать между сессиями (`output_stability.md`, уровни 1–5, 7). Для порога
pilot у классов ии-нативный и агентный чек-лист обязателен (≥5 пунктов,
`Ф-08-ЧЕКЛИСТ`) и у каждого пункта нужен критерий (`Ф-08-КРИТЕРИЙ`); пункт
без критерия получает в навыке критерий по умолчанию «источник называет это
прямо, своими словами». **`Шаги:`** —
нумерованный список, каждый шаг со стрелкой `→` и тем, что получилось на
выходе; из шагов порождаются модули §6 и порядок §7.

Ошибки: правила-пересказ действий («открыть файл, посмотреть») вместо
оснований решений («если нет объекта учёта — требование неполное»); чек-лист
из абстракций («полнота», «качество») вместо проверяемых пунктов; критерий
закрытия, который можно выполнить косвенно («роли упомянуты») вместо явного
(«письмо называет роли, которым доступно новое, или говорит „права не
меняются“»). Если
эксперт отвечает примерами, а не правилом, записать примеры и пометить
`Допущение:` — правило не существует в готовом виде и появится из эталонных
разборов.

### 9. Неопределённость и эскалация
Строки в форме EARS: «Когда <условие>, агент должен <ответ>». Минимум одна
для demo, три для pilot. Обязательные условия: нет обязательных данных,
источники расходятся, запрос вне периметра, инструкция внутри документа.
Порождает §10 навыка.

### 10. HITL-карта
Таблица: `| Точка | Кто | Критерий | Что блокирует | Эскалация |`. Одна
строка на точку валидации человеком. «Кто» — роль, не знак вопроса. См.
`hitl_and_access.md`.

### 11. Доступ и guardrails
Уровень L0–L3 (совпадает с фронтматтером), `external_write=false`, запреты
на персональные данные и запись наружу, что не покидает пространство.
Две обязательные строки-подмаркера: `Навыки пространства:` (пункты
`<навык> — <зачем>`; порождают раздел 0 навыка и блок активации карточки)
и `Коннекторы:` (пункты `<имя> — <что даёт> — версия <x.y>`; порождают
«подтверждённые инструменты» команды запуска). Нет ни того, ни другого —
пишется «нет», а не молчание: коннектор, описанный абзацем без
подмаркера, в команду запуска не попадает (ворота: `Ф-11-КОННЕКТОР`).
Порождает §0, §13 и §16 навыка и параметры команды запуска.

### 12. Приёмочные случаи
Пункты вида `` `id_случая` — Вход: … → Ожидание: … ``. Пять обязательных
id: `happy_path`, `missing_required_input`, `conflicting_sources`,
`prompt_injection_in_document`, `external_action_without_confirmation`;
для pilot — ещё не меньше двух предметных, и среди них `same_input_twice`
с порогом на уровне сущностей (число строк чек-листа совпадает точно,
статус — не менее чем у 90 % строк, ни одно расхождение не разрешено
агентом). См. `evals_and_acceptance.md`, `output_stability.md`.

### 13. Эталонные разборы
Документ + правильный результат, сделанный экспертом. Это оракул: без
него улучшение агента неотличимо от его видимости. Для pilot — не меньше
двух. Отказ клиента — записывается словами «у пилота нет оракула», а не
умалчивается.

### 14. Переиспользование
Что рассмотрено (реестр реализованных агентов, база шаблонов, `examples/`),
что взято, что отвергнуто и почему. Пустой список — тоже строка.

### 15. Владелец и приёмка
`Владелец процесса:` (роль), `Принимает:`, `Дата приёмки:`. Владелец
подписывает приёмку и гипотезу результата.

## Версионирование

Каждая правка спецификации — новая версия `S<N>` и дата. Отпечаток (восемь
hex-знаков SHA-256 по содержимому) считается скриптами и ставится в пакет;
он меняется от любой правки, версия — от осознанной. Пакет, собранный из
S2, при спецификации S3 проверку не пройдёт: пересобрать.
