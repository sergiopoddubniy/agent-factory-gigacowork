## Результат

Номер ТЗ: — (не присвоен) Дата: 2026-09-21 Инициатор: руководитель отдела закупок Аналитик: — Статус: черновик

### 1. Цель и обоснование
Исключить проведение документа «Заказ поставщику» без указания основания закупки. Заказчик — руководитель отдела закупок. Источник: письмо целиком (`письмо_03_конфликт.md`).

### 2. Объекты конфигурации
- `Документ.ЗаказПоставщику`, реквизит 006 «ОснованиеЗакупки» (Строка(150), выгрузка) — меняется обязательность: было «Необязательный» (выгрузка), запрошено «обязательный к заполнению всегда» (письмо). Новый реквизит не вводится, тип и длина не меняются. По этому изменению есть противоречие с текущим устройством конфигурации — см. Раздел 3, п.1 и вопрос №3.
- Для справки, без изменений: `Документ.ЗаявкаНаЗакупку` (в нём реквизита «Основание закупки» нет), `Обработка.СоздатьЗаказПоЗаявке` (создаёт «Заказ поставщику» по заявке и не заполняет «ОснованиеЗакупки»), `Документ.ПоступлениеТоваровУслуг` (реквизит 006 «ОснованиеЗакупки» копируется из заказа, тоже «Необязательный» в выгрузке) — эти объекты упомянуты, потому что от них зависит противоречие в п.1 Раздела 3.

### 3. Функциональные требования
1. **Описание:** реквизит «Основание закупки» документа «Заказ поставщику» становится обязательным к заполнению всегда.
   **Условие срабатывания:** проведение документа «Заказ поставщику».
   **Ожидаемое поведение:** если реквизит не заполнен — проведение блокируется, пользователю выводится сообщение «Укажите основание закупки».
   **Источник:** письмо, «сделать реквизит «Основание закупки» … обязательным к заполнению всегда: заказ без основания не должен проводиться, при попытке — сообщение «Укажите основание закупки»».
   ⚠ **`conflict_requires_review` (чек-лист №9, вопрос №3).** По выгрузке реквизит «ОснованиеЗакупки» — «Необязательный», и явно указано: «При автоматическом создании из «Заявки на закупку» остаётся пустым (в заявке такого реквизита нет)»; обработка «Создать заказ по заявке» (выгрузка): «Реквизит ОснованиеЗакупки заказа не заполняет.» Если реализовать требование как заявлено (обязательно всегда, блокировать проведение), все заказы, создаваемые автоматически по согласованной заявке, не смогут быть проведены без ручного дозаполнения поля — это гипотеза о причине расхождения, а не решение; какой вариант принять, определяет заказчик/архитектор 1С (см. вопрос №3). Оба описания показаны, агент вариант не выбирает.
2. **Описание:** создание заказа поставщику инициирует менеджер по закупкам.
   **Условие срабатывания:** оформление нового заказа.
   **Ожидаемое поведение:** менеджер по закупкам создаёт документ «Заказ поставщику».
   **Источник:** письмо, «Инициатор — менеджер по закупкам, который создаёт заказ.»
3. **Описание:** после доработки в базе не остаётся заказов поставщику без указанного основания закупки; печатная форма «Заказ» всегда выводит заполненное основание.
   **Источник:** письмо, «Ожидаемый результат: в базе нет ни одного заказа без основания, печатная форма «Заказ» всегда с заполненным основанием.» Достижимость этого результата для заказов, создаваемых автоматически, зависит от решения по вопросу №3.

### 4. Печатные формы
Не применяется: изменение не требуется. Источник: письмо, «Печатные формы не менять.» Справочно (выгрузка): макет ПФ_Заказ уже использует реквизит «ОснованиеЗакупки» — доработка не про добавление реквизита в форму, а про заполненность значения к моменту печати, что также зависит от решения по вопросу №3.

### 5. Права доступа
Не заполнено — вопрос №1 (см. реестр). Письмо не называет роли доступа к реквизиту «Основание закупки» и не говорит, что права не меняются. Дополнительно: выгрузка прав доступа не содержит («табличные части документов, права доступа и модули в выгрузку не включены», примечание выгрузки) — раздел не может быть закрыт и по выгрузке.

### 6. Миграция данных
Определяется ответом заказчика (вопрос №2). Письмо не говорит, что делать с уже существующими документами «Заказ поставщику», у которых «Основание закупки» не заполнено, — в том числе с заказами, созданными автоматически по заявкам, где, по устройству конфигурации, поле остаётся пустым по умолчанию.

### 7. Критерии приёмки
- Шаг: попытка провести «Заказ поставщику» без заполненного «Основание закупки» → Результат: документ не проводится, показывается сообщение «Укажите основание закупки». Источник: письмо. Критерий пригоден к проверке только после решения вопроса №3 — иначе не определено, распространяется ли блокировка на заказы, создаваемые автоматически по заявке.
- Остальные критерии приёмки (по правам доступа и по миграции существующих документов) не могут быть сформулированы до получения ответов на вопросы №1 и №2.

### Реестр открытых вопросов к заказчику
1. (пункт чек-листа 6) Каким ролям должен быть доступен реквизит «Основание закупки» документа «Заказ поставщику» — на чтение и на изменение? Права остаются как у документа в целом или должны быть ограничены?
2. (пункт чек-листа 7) Что делать с уже существующими документами «Заказ поставщику», у которых «Основание закупки» не заполнено: дозаполнить (кем и по какому правилу) или оставить как есть?
3. (пункт чек-листа 9, `conflict_requires_review`) Требование «обязательно всегда» противоречит текущему устройству конфигурации: реквизит «ОснованиеЗакупки» — «Необязательный», и при автоматическом создании заказа по согласованной заявке (обработка «Создать заказ по заявке») остаётся пустым, поскольку в документе «Заявка на закупку» такого реквизита нет, а сама обработка его не заполняет. Как поступить: (а) распространить обязательность и блокировку проведения на все заказы, включая созданные автоматически, и доработать «Заявку на закупку»/обработку «Создать заказ по заявке» так, чтобы основание передавалось или запрашивалось; (б) сделать реквизит обязательным только для заказов, создаваемых вручную; (в) иной вариант? Решение не принимается агентом.

## Неопределённости и допущения
- `missing_data`: не обнаружено — все обязательные входы (письмо, выгрузка, шаблон) получены и прочитаны.
- `conflict_requires_review`: пункт чек-листа №9 / вопрос №3 — требование «обязательно всегда» для «ОснованиеЗакупки» противоречит выгрузке (реквизит «Необязательный» и намеренно остаётся пустым при автосоздании заказа по заявке). Оба описания приведены в Разделе 3, п.1; решение не принято агентом.
- Допущение аналитика (гипотеза, не факт): вероятная причина конфликта — требование задумывалось для заказов, оформляемых вручную, а не для создаваемых автоматически по заявке; это предположение, статус конфликта оно не меняет.

## Ограничения
- Раздел 5 (Права доступа) не может быть закрыт ни по письму (не названо), ни по выгрузке (права доступа в неё не входят по примечанию выгрузки) — нужен ответ заказчика (вопрос №1).
- Раздел 6 (Миграция данных) не может быть закрыт без ответа заказчика (вопрос №2).
- Утверждение письма «в базе нет ни одного заказа без основания» не проверялось — доступ уровня L0, реальная информационная база не подключена, есть только приложенные файлы.
- `HITL_REQUIRED`: черновик ТЗ ждёт проверки аналитика 1С перед отправкой заказчику — реестр вопросов не пуст (3 позиции, включая 1 конфликт). Отдельно пункт с конфликтом (вопрос №3) ждёт решения архитектора 1С: использовать формулировку требования №1 из Раздела 3 как принятую в ТЗ нельзя до этого решения.
- Генерация и правка кода 1С, оценка трудоёмкости и сроков — вне периметра этого агента.
