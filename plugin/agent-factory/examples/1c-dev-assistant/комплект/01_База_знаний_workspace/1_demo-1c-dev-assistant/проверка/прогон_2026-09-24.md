## Результат

Номер ТЗ: — (не присвоен) · Дата: 2026-09-21 · Инициатор: руководитель отдела закупок (письмо, «От: руководитель отдела закупок») · Аналитик: — (не указан в обращении) · Статус: черновик

### 1. Цель и обоснование

Доработка документа «Заявка на закупку»: добавление реквизита «Основание закупки», значение которого затем переносится в документ «Заказ поставщику». Проблема бизнеса, по словам заказчика: согласующие вынуждены запрашивать основание закупки отдельно, в переписке, а заказы поставщику уходят без указания основания. Заказчик — руководитель отдела закупок (источник: письмо «Доработка заявки на закупку — основание»).

Ожидаемый результат для пользователя (письмо): «согласующие перестают запрашивать основание в переписке, заказы поставщикам создаются с заполненным основанием».

### 2. Объекты конфигурации

- **Документ.ЗаявкаНаЗакупку** (выгрузка, раздел «Документ.ЗаявкаНаЗакупку») — добавляется новый реквизит. Предлагаемое техническое имя — `ОснованиеЗакупки`, по аналогии с одноимённым реквизитом документа «Заказ поставщику» (это предложение аналитика, требует подтверждения; не вопрос заказчику и не конфликт). Тип — Строка(200) (письмо: «текстовое поле до 200 символов»). Обязательность на уровне метаданных — необязательный; проверка обязательности выполняется программно в момент перевода в статус «На согласовании» (см. Раздел 3, ФТ-2).
- **Документ.ЗаказПоставщику** (выгрузка, раздел «Документ.ЗаказПоставщику») — используется существующий реквизит «006 ОснованиеЗакупки Строка(150) Необязательный» как приёмник значения при создании заказа по заявке. По выгрузке: «При автоматическом создании из «Заявки на закупку» остаётся пустым (в заявке такого реквизита нет)» — доработка должна изменить это поведение. **Внимание — `conflict_requires_review`**: длина реквизита-приёмника (150 символов) меньше длины нового реквизита-источника (200 символов по письму); при переносе возможна потеря до 50 символов текста. Решение (увеличить длину поля заказа, ограничить длину поля заявки или обрезать текст при переносе) агент не принимает — вопрос №4 к заказчику и архитектору 1С.
- **Обработка.СоздатьЗаказПоЗаявке** (выгрузка) — по описанию сейчас «Реквизит ОснованиеЗакупки заказа не заполняет»; доработка должна добавить перенос значения из заявки в реквизит заказа с учётом ограничения выше.

### 3. Функциональные требования

1. **ФТ-1.** При создании документа «Заявка на закупку» реквизит «Основание закупки» доступен для заполнения инициатором. Условие срабатывания — создание заявки. Ожидаемое поведение — поле доступно для ввода текста до 200 символов. Источник: письмо, п.1 «Поле заполняет инициатор при создании заявки».
2. **ФТ-2.** При попытке перевода заявки в статус «На согласовании» (выгрузка: реквизит «006 СтатусЗаявки», значение «НаСогласовании» из Перечисление.СтатусыЗаявок) с незаполненным полем «Основание закупки» перевод статуса запрещается, выводится сообщение «Укажите основание закупки». Если поле заполнено — перевод выполняется как обычно. Источник: письмо, п.2. Открытый вопрос: кто именно выполняет перевод статуса, письмом не названо (вопрос №1).
3. **ФТ-3.** Согласующий видит значение поля «Основание закупки» в форме документа «Заявка на закупку» и как отдельную колонку в форме списка заявок (выгрузка: «Формы: ФормаДокумента, ФормаСписка»). Источник: письмо, п.3.
4. **ФТ-4.** При создании документа «Заказ поставщику» на основании согласованной «Заявки на закупку» значение поля «Основание закупки» переносится в одноимённый реквизит заказа. Источник: письмо, п.4. Открытые вопросы: кто инициирует создание заказа, письмом не названо (вопрос №1); длина полей не совпадает — `conflict_requires_review` (вопрос №4, см. Раздел 2).

### 4. Печатные формы

Не применяется: заказчик явно указал, что печатные формы менять не нужно (письмо: «Печатные формы менять не нужно»). Справочно: печатная форма «Заказ» (макет ПФ_Заказ, выгрузка) уже использует реквизит «ОснованиеЗакупки» документа «Заказ поставщику», поэтому после переноса значения из заявки форма отобразит его без доработки макета.

### 5. Права доступа

Определяется ответом заказчика (вопрос №2). Письмо называет, кто заполняет поле (инициатор) и кто его видит (согласующий), но не говорит, каким ролям доступно чтение/изменение нового реквизита, и не говорит, что права не меняются. Выгрузка также не содержит данных о правах доступа (примечание выгрузки: «права доступа и модули в выгрузку не включены»), поэтому раздел не может быть заполнен без ответа заказчика.

### 6. Миграция данных

Определяется ответом заказчика (вопрос №3). Письмо не говорит, что делать с уже существующими заявками и заказами поставщику (заполнять ли для них «Основание закупки» задним числом, оставить пустыми или иное) — раздел не заполняется по умолчанию.

### 7. Критерии приёмки

1. Инициатор создаёт заявку на закупку → поле «Основание закупки» доступно для заполнения текстом до 200 символов.
2. Инициатор пытается перевести заявку в статус «На согласовании» с пустым полем «Основание закупки» → перевод блокируется, выводится сообщение «Укажите основание закупки».
3. Поле «Основание закупки» заполнено, заявка переводится в статус «На согласовании» → перевод выполняется.
4. Согласующий открывает форму заявки и список заявок → видит значение поля «Основание закупки» в форме и в отдельной колонке списка.
5. По согласованной заявке создаётся заказ поставщику → поле «Основание закупки» заказа заполнено значением из заявки (с оговоркой по длине поля — см. вопрос №4, конфликт не разрешён).
6. Печатная форма «Заказ» формируется по заказу, созданному из заявки → в форме отображается перенесённое основание закупки; макет печатной формы не изменён.

### Реестр открытых вопросов к заказчику

1. Кто выполняет перевод заявки на закупку в статус «На согласовании» и кто инициирует создание заказа поставщику по согласованной заявке — письмо не называет роль исполнителя для этих действий (чек-лист, п.2).
2. Каким ролям должен быть доступен реквизит «Основание закупки» на чтение и на изменение — письмо об этом не говорит, и права не названы «неизменными» (чек-лист, п.6).
3. Что делать с уже существующими заявками и заказами поставщику при внедрении доработки — нужно ли заполнять «Основание закупки» задним числом (чек-лист, п.7, миграция).
4. `conflict_requires_review`: новый реквизит «Основание закупки» заявки — до 200 символов (письмо), а одноимённый существующий реквизит документа «Заказ поставщику» — Строка(150) (выгрузка, реквизит 006). При прямом переносе возможна потеря до 50 символов текста. Как поступить — увеличить длину поля заказа, ограничить длину поля заявки или обрезать текст при переносе? Решение не принимается агентом (чек-лист, п.9).

## Неопределённости и допущения

- `missing_data`: нет — все три обязательных входа получены (письмо, выгрузка конфигурации, шаблон ТЗ). Данных о правах доступа в выгрузке нет в принципе (примечание выгрузки), это ограничивает раздел 5, но не является отсутствием обязательного входа.
- `conflict_requires_review`: новый реквизит «Основание закупки» заявки заявлен на 200 символов, а существующий одноимённый реквизит документа «Заказ поставщику», в который его нужно переносить, — Строка(150) (выгрузка). Оба значения показаны выше (Раздел 2, вопрос №4); решение не принято.
- Допущение аналитика: техническое имя нового реквизита предложено как `ОснованиеЗакупки` по аналогии с реквизитом «Заказ поставщику» — требует подтверждения при постановке задачи разработчику.
- Допущение: обязательность нового реквизита реализуется как программная проверка на событии перевода статуса, а не как признак «Обязательный» на уровне метаданных, — это следует из письма (поле не обязательно при создании, обязательно к моменту перевода статуса), явно способом реализации заказчик не указал.

Для этой задачи обязательны три входа: запрос бизнеса, выгрузка описания конфигурации (список объектов метаданных с реквизитами, сделанная штатными средствами) и шаблон ТЗ (§5 навыка). Письмо и шаблон получены, выгрузки нет — вы сами это отметили («Выгрузки конфигурации у меня сейчас нет»). Отсутствие обязательного входа даёт статус `missing_data`: работа над результатом не начинается без уточнения (§5, §7 навыка).

Без выгрузки нельзя закрыть как минимум три пункта чек-листа полноты, обязательного для каждого результата этого агента: «Объект конфигурации и реквизит, которых касается запрос» (нужно подтвердить, что документ «Заявка на закупку» есть в выгрузке), «Права доступа к новому (роли)» и «Расхождения запроса с выгрузкой» (нужно сверить тип, длину и обязательность нового реквизита «Основание закупки» с тем, что уже есть у документов «Заявка на закупку» и «Заказ поставщику»). От этого напрямую зависят разделы шаблона «2. Объекты конфигурации» и «7. Критерии приёмки» — заполнить их без сверки с выгрузкой значило бы выдать предположение за проверенный факт (§9 навыка).

### 2. Объекты конфигурации

### 3. Функциональные требования
1. **Описание:** реквизит «Основание закупки» документа «Заказ поставщику» становится обязательным к заполнению всегда.
   **Условие срабатывания:** проведение документа «Заказ поставщику».
   **Ожидаемое поведение:** если реквизит не заполнен — проведение блокируется, пользователю выводится сообщение «Укажите основание закупки».
   **Источник:** письмо, «сделать реквизит «Основание закупки» … обязательным к заполнению всегда: заказ без основания не должен проводиться, при попытке — сообщение «Укажите основание закупки»».

   **Ожидаемое поведение:** менеджер по закупкам создаёт документ «Заказ поставщику».

1. Отчёт «Заявки без основания» отбирает заявки на закупку за период, у которых поле «Основание закупки» не заполнено. Источник: письмо, «список заявок на закупку за период, у которых поле «Основание закупки» пустое». Объект, к которому фактически относится фильтр, зависит от ответа на Вопрос №1 (см. раздел 2); период — от ответа на Вопрос №4.
2. Отчёт содержит колонки: номер, дата, подразделение, инициатор, статус, сумма. Источник: письмо, «с колонками номер, дата, подразделение, инициатор, статус, сумма»; все шесть сверены с реквизитами «Заявки на закупку» в выгрузке, расхождений нет.
3. Руководитель подразделения видит в отчёте только заявки своего подразделения; руководитель отдела закупок — по всем подразделениям. Источник: письмо, «Отчёт нужен руководителям подразделений (по своему подразделению) и мне (по всем)».
4. Отчёт запускается из меню «Закупки». Источник: письмо, «Запускать из меню «Закупки»». Наличие такого пункта меню в конфигурации не проверялось: выгрузка не включает состав меню/подсистем (см. «Ограничения»).
5. Пользователю нужно видеть отчёт еженедельно по понедельникам. Источник: письмо, «Хотим видеть его еженедельно по понедельникам». Не названо, что это означает технически — регулярный ручной запуск или автоматическая доставка (Вопрос №4); требование неполное, способ по умолчанию не закладывается.

#### 4. Печатные формы
Не применяется: запрос не описывает изменений печатных форм; отчёт — самостоятельный объект, не печатная форма документа.

#### 5. Права доступа
- Роль «Руководитель подразделения» — чтение отчёта, данные ограничены своим подразделением. Источник: письмо.
- Роль «Руководитель отдела закупок» — чтение отчёта по всем подразделениям. Источник: письмо.
- Доступ иным ролям (инициаторы заявок, согласующие и т. п.) письмом не запрошен и не рассматривается.

#### 6. Миграция данных
Определяется ответом заказчика (Вопрос №3): письмо не говорит, нужно ли и как учитывать в отчёте заявки, созданные до внедрения поля «Основание закупки».

#### 7. Критерии приёмки
Пока не сняты Вопросы №1 и №4, полный набор критериев сформулировать нельзя. Проверяемо уже сейчас:
- Шаг: пользователь с ролью «Руководитель подразделения» открывает отчёт → Результат: видит только заявки своего подразделения, колонки — номер, дата, подразделение, инициатор, статус, сумма.
- Шаг: пользователь с ролью «Руководитель отдела закупок» открывает отчёт → Результат: видит заявки по всем подразделениям с тем же набором колонок.
- Критерии по фильтру «без основания», периоду отчёта и способу регулярного получения — после ответов на Вопросы №1 и №4.

#### Реестр открытых вопросов к заказчику
1. В выгрузке конфигурации реквизит «Основание закупки» отсутствует у документа «Заявка на закупку» (в описании конфигурации прямо сказано: «в заявке такого реквизита нет»); он найден у документов «Заказ поставщику» и «Поступление товаров и услуг». Уточните: нужно ли добавить этот реквизит в «Заявку на закупку» (тогда это отдельная доработка сверх отчёта), или отчёт должен строиться по документу «Заказ поставщику» / «Поступление товаров и услуг»?
2. Что изменится в работе руководителей после получения отчёта (например, требование дозаполнить основание, приостановка каких-либо действий и т. п.), помимо самого факта увидеть список?
3. Нужно ли и как учитывать в отчёте (или дозаполнять) заявки, созданные до внедрения поля «Основание закупки»?
4. За какой период отчёт должен отбирать заявки при каждом открытии, и каким способом вы хотите получать его еженедельно по понедельникам — ручной запуск из меню «Закупки» каждый раз, или автоматическая рассылка/подписка средствами 1С (и если рассылка — кому и в каком виде)?

### Черновик ТЗ по шаблону компании

Номер ТЗ: присваивается при регистрации (не назначен)   Дата: 2026-09-21   Инициатор: руководитель отдела закупок (по письму)   Аналитик: не указан в переписке   Статус: черновик

**1. Цель и обоснование**
Отдел закупок просит доработать документ «Заявка на закупку»: добавить реквизит «Основание закупки», чтобы фиксировать, зачем нужна закупка (номер проекта, договор, служебная записка), и передавать эту информацию дальше в заказ поставщику. Заказчик — руководитель отдела закупок. Проблема бизнеса: согласующие вынуждены запрашивать основание закупки в переписке отдельно от заявки (источник: письмо, «Ожидаемый результат»).

**2. Объекты конфигурации**
- `Документ.ЗаявкаНаЗакупку` — добавить новый реквизит. Предлагаемое техническое имя (предложение аналитика, требует подтверждения при постановке разработчику): `ОснованиеЗакупки`, тип `Строка(200)`, по аналогии с одноимённым реквизитом документов «Заказ поставщику» и «Поступление товаров и услуг» (источник: письмо — «текстовое поле до 200 символов»; выгрузка — `Документ.ЗаявкаНаЗакупку`, реквизиты 001–010).
- `Документ.ЗаказПоставщику` — уже имеет реквизит 006 «ОснованиеЗакупки» (`Строка(150)`, необязательный), который сейчас остаётся пустым при автосоздании из заявки. Это поле — цель переноса значения по требованию 4 письма. Расхождение длины с новым полем заявки (200 vs 150) — см. вопрос №4 / `conflict_requires_review` (источник: выгрузка, `Документ.ЗаказПоставщику`, реквизит 006).
- `Обработка.СоздатьЗаказПоЗаявке` — требует доработки: сейчас реквизит `ОснованиеЗакупки` заказа явно не заполняется («Реквизит ОснованиеЗакупки заказа не заполняет», выгрузка). Для выполнения требования 4 письма обработку нужно изменить, чтобы она переносила значение из заявки.

**3. Функциональные требования**
1. Заполнение поля инициатором. Условие: создание документа «Заявка на закупку». Поведение: поле «Основание закупки» доступно для ввода инициатору, тип — текст до 200 символов. Источник: письмо, требование 1.
2. Обязательность при переводе статуса. Условие: попытка перевода заявки в статус «На согласовании». Поведение: если поле пусто — перевод блокируется, выводится сообщение «Укажите основание закупки». Источник: письмо, требование 2. Кто выполняет перевод статуса — не назван (вопрос №1).
3. Видимость согласующему. Условие: открытие формы заявки или списка заявок. Поведение: поле «Основание закупки» отображается в форме документа и отдельной колонкой в списке заявок. Источник: письмо, требование 3.
4. Перенос основания в заказ поставщику. Условие: создание заказа поставщику по согласованной заявке (обработка «Создать заказ по заявке»). Поведение: значение «Основание закупки» заявки переносится в реквизит «ОснованиеЗакупки» заказа. Источник: письмо, требование 4; выгрузка — `Обработка.СоздатьЗаказПоЗаявке` (сейчас поле не заполняет). Открыто: кто инициирует создание заказа — не назван (вопрос №1); длина целевого поля заказа (150) меньше длины нового поля заявки (200) — конфликт, решение не принято агентом (вопрос №4, `conflict_requires_review`).

**4. Печатные формы**
Не изменяются — прямое указание письма: «Печатные формы менять не нужно». Существующая печатная форма «Заказ» (макет ПФ_Заказ) уже выводит реквизит `ОснованиеЗакупки` (выгрузка); после реализации требования 4 форма покажет перенесённое значение без изменения самого макета. Печатная форма «Заявка» (макет ПФ_Заявка) в выгрузке не описана как использующая новое поле — отдельного запроса на её изменение в письме нет.

**5. Права доступа**
Определяется ответом заказчика (вопрос №2). Из письма известно, что поле заполняет инициатор (требование 1) и видит согласующий (требование 3), но кто именно имеет доступ на чтение/изменение и меняются ли права других ролей — не указано.

**6. Миграция данных**
Определяется ответом заказчика (вопрос №3). Письмо не говорит, что делать с реквизитом «Основание закупки» у уже существующих (созданных до внедрения) заявок на закупку и заказов поставщику.

**7. Критерии приёмки**
1. Инициатор создаёт заявку и заполняет поле «Основание закупки» (до 200 символов) → поле сохраняется без ошибок.
2. Заявка с пустым полем «Основание закупки» переводится в статус «На согласовании» → перевод блокируется, выводится сообщение «Укажите основание закупки».
3. Заявка с заполненным полем переводится в статус «На согласовании» → перевод проходит без ошибок.
4. Согласующий открывает форму заявки и список заявок → видит значение поля «Основание закупки» в форме и колонкой в списке.
5. По согласованной заявке через обработку «Создать заказ по заявке» создаётся заказ поставщику → реквизит «ОснованиеЗакупки» заказа заполнен значением из заявки (порядок работы с расхождением длины — по решению вопроса №4).
6. Печатная форма «Заказ» открыта по такому заказу → в форме отображается перенесённое основание, макет не изменён.

**Реестр открытых вопросов к заказчику**
1. Кто именно переводит заявку в статус «На согласовании» и кто инициирует создание заказа поставщику по согласованной заявке — роли в письме не названы (пункт чек-листа 2).
2. Каким ролям должен быть доступен реквизит «Основание закупки» на чтение и на изменение — помимо того, что его заполняет инициатор, а видит согласующий (пункт чек-листа 6)?
3. Нужно ли заполнять реквизит «Основание закупки» для уже существующих заявок на закупку и заказов поставщику, и если да — как (пункт чек-листа 7)?
4. `conflict_requires_review`: новый реквизит «Основание закупки» заявки определён как текстовое поле до 200 символов, а существующий реквизит «ОснованиеЗакупки» документа «Заказ поставщику», в который это значение должно переноситься по требованию 4, — `Строка(150)`. Как поступить: увеличить длину поля заказа до 200, ограничить новое поле заявки 150 символами, либо обрезать/предупреждать при переносе текста длиннее 150 символов? Решение не принимается агентом (пункт чек-листа 9).

## Неопределённости и допущения

- `missing_data`: не применимо — все обязательные входы (письмо, выгрузка, шаблон) получены полностью; недостающие внутри самого запроса сведения (исполнители действий, права доступа, миграция) вынесены как вопросы №1–3 в реестр вопросов к заказчику, а не как отсутствие входных данных.
- `conflict_requires_review`: вопрос №4 — длина нового реквизита «Основание закупки» заявки (200 символов, по письму) не совпадает с длиной существующего реквизита «ОснованиеЗакупки» документа «Заказ поставщику» (150 символов, по выгрузке), в который это значение должно переноситься по требованию 4 письма. Оба значения показаны выше, решение не принято агентом.
- Допущение аналитика (не вопрос заказчику, требует подтверждения при постановке разработчику): предлагаемое техническое имя нового реквизита — `ОснованиеЗакупки` в `Документ.ЗаявкаНаЗакупку`, по аналогии с одноимённым реквизитом документов «Заказ поставщику» и «Поступление товаров и услуг».

## Ограничения

- Табличные части документов, права доступа и модули не входят в выгрузку (указано в её примечании) и не назывались в письме — поэтому раздел «Права доступа» шаблона ТЗ не закрыт без ответа заказчика (вопрос №2).
- Состав полей печатной формы «Заявка» (макет ПФ_Заявка) не проверялся — в выгрузке он не описан.
- `HITL_REQUIRED`: черновик ТЗ не передаётся заказчику на согласование до решения аналитика 1С по вопросам №1–3; конфликт по вопросу №4 требует рассмотрения архитектором 1С; в целом ТЗ — согласования руководителем направления 1С (§11 навыка).
- Работа велась только по трём приложенным файлам (контур `demo`, уровень доступа L0); к информационной базе 1С и другим внешним системам агент не подключался, никаких записей и обращений не выполнялось. Внешних действий в рамках этого запроса не требовалось — `SIM_TOOL_CALL`/`SIM_TOOL_RESULT` не понадобились.
